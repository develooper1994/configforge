# X - more formats, and what a format is

The group for `docs/Roadmap.md` lines 156-225 ("More formats, and what a
format is", asked 2026-11-13) and lines 1013-1037 (the serialization
sources, laid out by what they share). Every card here adds a codec to the
library `lib/serialize/` the way CBOR was added (D-91,
`lib/serialize/src/cbor.c`) or measures what that library does with them.
The first card, X-1, spells out every file a new binary codec touches; the
later codec cards say "as X-1" and name only what differs. Each card is
read cold against the tree before it opens (docs/Plan.md, "Read again
after the layout changes"); line numbers are those of `main` at b507f16 (checked 2026-11-26).

Versions (docs/Maintaining.md:99-114): X-1 to X-17 belong to **2.1.0**
("more formats"): their CHANGELOG heading is `## 2.1.0 — unreleased` (the
first of them creates it above `## 1.9.0 — unreleased`, `CHANGELOG.md:6`).
X-18 to X-21 belong to **1.8.0**'s theme ("the serialization sources laid
out by what they share"); 1.8.0 is released (`CHANGELOG.md:76`), so their
entries go under `## 1.9.0 — unreleased` and each card says so.

Order: X-18 to X-21 do not wait for X-1 to X-17 and should land first
(Roadmap: "before MISRA and before the P cards: moving the code after
they have touched it is moving it twice"). Once X-19 has landed, a new
codec's writer is `<fmt>_emit.c` and its reader `<fmt>.c` (D-150), and
X-1's file list reads that way; a codec that landed before X-19 is split
by X-19.

Decisions D-141 to D-150 are allotted: D-141 MessagePack and the pattern
every binary codec after it follows; D-142 the other self-describing binary
formats (BSON, UBJSON, Smile, Ion, Bencode: each card appends its own
paragraph to D-142 with a "Built:" line); D-143 property lists; D-144 HCL;
D-145 HOCON; D-146 KDL; D-147 TLV as it is met; D-148 formats bound to a
schema; D-149 the codec benchmark and text handed over in place; D-150 the
serialization sources' layout.

Not here: "whole or as a stream" (`docs/Roadmap.md:188-`) is the 2.0 stream
reader, the maintainer's.

Common to the codec cards (so a card need not say it again):

* Every new codec is an option of the build, on by default, with no
  dependency (`docs/Roadmap.md:192-194`: every format is an option of the
  build): `CF_WITH_<NAME>`, in the list `CF_FEATURES`
  (`cmake/ConfigForgeOptions.cmake:112-130`).
* Every text a codec reads is checked UTF-8 by `cf_text_is_utf8`
  (`lib/text/include/configforge/cf_text.h`; D-108) and refused by name
  when it is not. A byte string is refused by name as in CBOR (D-91): a
  configuration has no type for bytes.
* Every refusal goes through `cf_error_set` then `cf_error_place`, one
  reason from `CF_REASON_*` (D-107), as `cbor_fail` does (`cbor.c:91-96`);
  the place is `<file>, byte <n>` (D-91, "Places").
* A length, a count and a depth are checked against the bytes left and
  `CF_MAX_DEPTH` before anything is read or reserved (D-91, D-82), so a
  count of four billion costs nothing.
* Text a binary format stores whole is handed to the sink where it lies in
  the document, not copied: `cf_value_text(&v, (const char*)p, n)` with `p`
  into `in->p` (as `cbor_definite` does, `cbor.c:214-230`).
* The codec is read and written unless its card says why not. The writer is
  a `cf_encoder` over `cf_sink` (`cbor.c:925-945`), never deterministic, and
  a literal `${` stays literal (D-91): the encoder doubles each `${` in a
  text it writes, with `CF_CODEC_BINARY` set and `cf_encoder_head` first in
  its state (`cbor.c:711-715`).

## X-1 - MessagePack: reader, writer, vectors, fuzz target

* **id**: X-1
* **goal**: `cf_codec_by_name("msgpack")` reads and writes MessagePack (the specification at github.com/msgpack/msgpack, `spec.md`) as the JSON-shaped model of D-91, is in every preset that has CBOR, is read to the values the msgpack-test-suite states, is fuzzed, and is documented.
* **why**: a device or service that keeps its settings in MessagePack has them copied into JSON to be read, and the copy is what `explain()` then names (D-91's question again). This is the first of the formats of `docs/Roadmap.md:168-170` and the pattern the next five follow.
* **needs**: nothing (the codec table and the CBOR reader it copies from are in the tree).
* **size**: large (a codec of about 700 lines and its wiring in about 20 files; a worker that passes ~60 turns stops, and the writer becomes X-1b).
* **version**: 2.5.0
* **status**: open
* **decided**:
  * **Names.** Option `CF_WITH_MSGPACK` ("the MessagePack codec", ON); source `lib/serialize/src/msgpack.c`; codec `cf_codec_msgpack`; name `"msgpack"`; extensions `".msgpack;.mpk"`; test `lib/config/tests/test_msgpack.c`; feature name `"msgpack"`. Caps: `CF_CODEC_READ | CF_CODEC_WRITE | CF_CODEC_TYPED | CF_CODEC_ARRAYS | CF_CODEC_BINARY` (as `cf_codec_cbor`, `cbor.c:947-956`); a read-only build (`!CF_WITH_EMIT`) drops WRITE and the encoder (`cbor.c:958-968`).
  * **The model is D-91's.** A map with text keys at the top; maps, arrays, integers, `float 32` and `float 64`, strings, `false`, `true`, `nil` (= null) inside. Its row in `cf_formats[]` is `CF_HOLDS_ALL`, `NO_LIMIT`, `DEPTH_MAX` (`codec.c:336`, copied with the name changed).
  * **Refused by name** (reason `CF_REASON_UNSUPPORTED` unless noted): `bin 8/16/32` ("a byte string, which a configuration has no type for"); every `ext` and `fixext` type, the timestamp (-1) included ("an extension type <n>": the timestamp has no place in the JSON model); the byte `0xc1` ("a byte MessagePack never uses", `CF_REASON_SYNTAX`); a key that is not a `str` ("a key that is a <what>"); `uint 64` above 9223372036854775807 ("an integer past 64 bits signed", `CF_REASON_NUMBER_RANGE`, as D-91). An integer is read from its shortest form or any longer one (non-minimal is well-formed, as CBOR's heads are). `float 32` is read as the `double` of the same value (`cf_f64_from_f32_bits`, D-91's helper). Infinity and NaN are the text `inf`, `-inf`, `nan` with `textual` set (D-62), as CBOR's.
  * **Duplicate keys** are read, the later winning (D-91). **The top** is a map (`0x80-0x8f`, `0xde`, `0xdf`) and nothing may follow it ("data after the document", `CF_REASON_TRAILING`); no byte order mark and no self-describe tag exist, so nothing is skipped.
  * **Reading** is `msgpack_item(s, name, nlen)`, one function per kind as `cbor_item` is (`cbor.c:581-644`); nesting is a depth counter against `CF_MAX_DEPTH`. A `str` is checked with `cf_text_is_utf8` ("a string that is not UTF-8", `CF_REASON_UTF8`). A count (`array 16/32`, `map 16/32`, `str 8/16/32` length) is compared with the bytes left before use ("a length of <n> bytes, <m> are left", `CF_REASON_TRUNCATED`). Places: `<file>, byte <n>`, n the offset of the item's first byte.
  * **Writing: a container's head is always the 32-bit form** (`array 32` `0xdd`, `map 32` `0xdf`, the count as four bytes), because the events do not say how many members a container has until its end (D-91) and MessagePack has no indefinite length. The encoder keeps, for each open container, the offset of its count and a running count (`struct { size_t at; cf_u32 n; } open[CF_MAX_DEPTH]` in `msgpack_enc`, whose first member is the `cf_encoder_head`), and at `end` patches the four bytes **only if** they were stored (`at + 4 <= out->cap`): a measuring sink (`cf_sink_init(&s, NULL, 0)`) keeps only `len` and needs no patch. A map's count is its pairs. Rejected: a second walk (D-91); buffering a container (no memory to buffer in); `array 16` when it fits (the encoder cannot know). Text and numbers are in the shortest form (`fixstr`, `str 8/16/32`; `positive fixint`, `uint 8..64`, `negative fixint`, `int 8..64`); a real is `float 32` when exactly a float, else `float 64`. Keys in the walk's order.
  * **Detection from content: none.** `0x80-0x8f` are UTF-8 continuation bytes like CBOR's, but `0xde` and `0xdf` are lead bytes text may begin with, and CBOR owns `0xa0-0xbb` (`detect.c:184-190`). A MessagePack document is chosen by extension or by name; `look_orders` (`detect.c:168-174`) does not change, and `test_detect.c` gets a case that `81 a1 61 01` is read by no detector. Rejected: trying MessagePack last for every unrecognised binary file (a false positive reads garbage as a map).
  * **D-141**, to copy into `docs/Decisions.md` after D-112 (heading `## D-141 — MessagePack, and what a binary codec after CBOR follows`) with this text: "**Question.** Can a configuration kept in MessagePack be read as itself? **Decision.** Yes: `CF_WITH_MSGPACK`, the JSON model of D-91 with byte strings and every extension type refused by name, the top a map, duplicate keys read, places by byte offset. Written with a 32-bit count in every container head, patched at the container's end when its bytes were stored, because MessagePack has no indefinite length and the events carry no count. Not detected from content. **The pattern.** Every later binary codec (D-142) states the same six things: what it refuses, its top, its duplicate keys, its places, how it writes a count, its detection. **Held to.** `test_msgpack`; the msgpack-test-suite at its pinned commit (N of N read, the rest refused by name for the model); the reader fuzzed (`fuzz.msgpack`)." The worker replaces N with the measured score.
  * **Vectors.** `github.com/kawanet/msgpack-test-suite`, its JSON export (`dist/msgpack-test-suite.json`: each exam has `msgpack: [hex, ...]` equivalent encodings and the value under `nil`, `bool`, `number`, `string`, `array`, `map`, `binary`, `bignum` or `timestamp`). Fetched like `cbor-test-vectors` (`scripts/check/conformance.py:14-22, 400-427`) into `<suites-dir>/msgpack-test-suite` at a commit the worker records in `docs/Conformance.md` (table at line 54). Each exam's value is wrapped as `{"v": <value>}` (`81 a1 76` then the encoding), so a lone value is a configuration, as `conform.c` wraps JSON's. Exams of kind `binary`, `bignum` and `timestamp` are counted apart as "refused for the model" (as `MODEL` does for YAML, `conformance.py:58-70`). The invalid set, there being none in the suite, is `INVALID_MSGPACK` in `conformance.py`, scored as `INVALID_CBOR` is (`conformance.py:368-399`): a truncated `str 8`, `c1`, a map cut after a key, an `array 32` of 4294967295 items with no bytes, a `str` of bytes `ff fe`, a map key `01`, a byte after the map.
  * **Reference library.** Where the Python package `msgpack` is installed (as `json5` is, `scripts/buildenv/dev-setup.sh`), `conformance.py` also writes one document through `msgpack.packb` and the same document through `cf_emit`, and checks both read to the same keys (`docs/Roadmap.md:194-196`): a function `msgpack_values` next to `cbor_values` (`conformance.py:430-`), scored as `msgpack-values`; skipped with a line where the package is absent.
* **files**: create `lib/serialize/src/msgpack.c`, `lib/config/tests/test_msgpack.c`. Change, in this order: `cmake/ConfigForgeOptions.cmake:17` (the `option`) and `:117` (`CF_FEATURES`, after `CBOR`); `cmake/templates/cf_build_options.h.in:23` (`#define CF_WITH_MSGPACK @CF_OPT_MSGPACK@`); `lib/port/include/configforge/cf_build_options.h` (regenerated by the configure step, not edited); every `cmake/profiles/*.cmake` that sets `CF_WITH_CBOR` (`grep -l CF_WITH_CBOR cmake/profiles`: `default` and `misra` at line 7, `full`, `minimal`, `server`, `embedded-json`, `embedded-cbor`): the same line for MSGPACK, ON where CBOR is ON, OFF in `minimal`, `embedded-json` and `embedded-cbor`; `lib/serialize/CMakeLists.txt:33` (`MSGPACK:msgpack` in the `foreach`); `lib/serialize/src/codec.c:37-38` and `:61-62` (extern and `cf_codecs[]` entry, in `#if CF_WITH_MSGPACK`) and `:336` (the `cf_formats[]` row); `lib/config/src/core/version.c:55-57` (the feature list); `lib/config/tests/CMakeLists.txt:77` (`test_msgpack`); `lib/config/tests/test_features.c:44`, `test_kinds.c:43` (binary: msgpack), `test_detect.c` (the no-detection case); `lib/serialize/tests/test_holds.c:29` and `:277`, `tests/codec/pairs.c:36`, `tools/codec/pairs.c:17` (the writer lists: `"msgpack"` after `"cbor"`); `tests/codec/convert.cmake:428-470` (a round trip `a.json` to `a.msgpack` and back, as cbor's); `tests/fuzz/CMakeLists.txt:47-48` (reader) and `:56-70` (`all_readers`: after `ber`, so its number is 15); `tests/fuzz/libfuzzer.c:51-56` (`#elif CF_FUZZ_TARGET == 15` then `feed_codec("msgpack", &v);`); `lib/config/tests/test_fuzz.c:558-562, 677, 694, 818, 880` (a seed `g_msgpack` holding a member of each kind the codec takes, `write_seed("seed_msgpack", ...)`, `fuzz_bytes(cf_codec_by_name("msgpack"), ...)`); `scripts/check/conformance.py`; `scripts/check/pairs.py:44` (the vectors as pairs); `tests/conformance/floor.txt` (`msgpack <valid> <invalid>`, `msgpack-values <n>`: the scores the first run gives); `scripts/generate/amalgamate.py:76` (`serialize/src/msgpack.c` after `cbor.c`). ## X-2 - BSON

* **id**: X-2
* **goal**: `cf_codec_by_name("bson")` reads and writes BSON 1.1 (bsonspec.org) as the JSON model, held to the MongoDB `bson-corpus`, fuzzed, documented.
* **why**: configuration kept in a document database (MongoDB's own exports, `mongodump`) is BSON; as for MessagePack, the copy to JSON is what `explain()` would name.
* **needs**: X-1 (its wiring, its test shape, D-141's six points).
* **size**: large
* **version**: 2.5.0
* **status**: open
* **decided**: Every item of X-1 holds with the names changed: option `CF_WITH_BSON`, `lib/serialize/src/bson.c`, `cf_codec_bson`, `"bson"`, `".bson"`, test `test_bson.c`, fuzz number 16 (`all_readers` after `msgpack`).
  * **Top.** The BSON document itself: `int32` total length (little-endian, counting itself and the final `00`), elements, `00`. The length must equal the bytes given ("the length says <n> bytes, the document has <m>", `CF_REASON_SYNTAX`); nothing follows. An element is a type byte, a `cstring` name (UTF-8 checked), the value.
  * **Read**, by type byte: `01` double (Infinity and NaN as the text, D-62); `02` string (`int32` length counting the closing `00`, UTF-8; the last byte must be `00`; a NUL inside is held, as `CF_HOLDS_NUL` says; a length of 0 is "a string of length 0", `CF_REASON_SYNTAX`); `03` document (a table); `04` array (a document whose names must be "0", "1", ... in order: any other name is refused "an array element named <name>, expected <k>", `CF_REASON_SYNTAX`); `08` boolean (`00` or `01`, else "a boolean of <n>", `CF_REASON_SYNTAX`); `0A` null; `10` int32; `12` int64.
  * **Refused by name** (`CF_REASON_UNSUPPORTED`, "<kind>, which a configuration has no type for"): `05` binary, `06` undefined, `07` ObjectId, `09` UTC datetime, `0B` regular expression, `0C` DBPointer, `0D` JavaScript, `0E` symbol, `0F` JavaScript with scope, `11` timestamp, `13` Decimal128, `FF` min key, `7F` max key; any other byte "an unknown element type <n>" (`CF_REASON_SYNTAX`). Rejected: reading ObjectId or datetime as text (an encoding nobody asked for, D-91).
  * **Duplicate names** are read, the later winning (D-91, D-141). **Places**: `<file>, byte <n>`, n the offset of the element's type byte.
  * **Writing: a container's length is a prefix**, patched as X-1 patches a count: an `int32` slot of four zero bytes at the open, patched at the close when `at + 4 <= out->cap` with the number of bytes from the slot to the end counting the slot and the final `00`. An array's element names are the decimal of the running count. A text is `02`, its length plus one as `int32`, the bytes, `00`. An integer is `10` when it fits an int32, else `12`. A real is `01`. A null is `0A`. The top table is the document. `${` doubled as in X-1.
  * **Detection from content: none** (the first byte is the low byte of a length: any byte is possible). By extension or by name.
  * **D-142**, created by this card in `docs/Decisions.md` after D-141 (heading `## D-142 — The other self-describing binary formats, one model`): "Each reads the JSON model of D-91 and D-141, names what it refuses, and writes a count by patching or by an end marker; one paragraph a format follows, each ending `Built: <card>`." Then the paragraph "**BSON.** ..." giving the refusals, the top (the document, its length checked), duplicate names read, places by byte offset, the length prefix patched, no detection. `Built: X-2.`
  * **Vectors.** `github.com/mongodb/specifications`, `source/bson-corpus/tests/*.json` (each file: `valid` cases with `canonical_bson` hex and `canonical_extjson`; `decodeErrors` with `bson` hex; `parseErrors` are extended JSON and are not read). Fetched as X-1's suite at a commit the worker records in `docs/Conformance.md`. A valid case whose type is in the read list is read; the files of the refused kinds (`binary`, `dbpointer`, `code`, `code_w_scope`, `symbol`, `timestamp`, `datetime`, `oid`, `regex`, `decimal128`, `minkey`, `maxkey`, `undefined`) are counted "refused for the model" as `MODEL` counts YAML's (`conformance.py:58-70`); every `decodeErrors` case must be refused. The expected keys are those of `canonical_extjson`: `bson_values` (next to `cbor_values`, `conformance.py:430-`) unwraps `$numberInt`, `$numberLong` and `$numberDouble` for the read kinds. The valid documents are already documents: no wrapping.
  * **Reference library.** Where the Python package `pymongo` (module `bson`) is installed, `bson_values` writes one document with `bson.encode` and with `cf_emit` and checks the same keys; skipped with a line otherwise.
* **files**: as X-1's list with `bson` for `msgpack` and fuzz seed `g_bson`; `test_detect.c` pins that `0c 00 00 00 ...` is claimed by no detector; `docs/Decisions.md` gets D-142 and its index row.
* **steps**: X-1's steps 1-10 with: step 3's exact writer bytes for `{"a": 1, "b": [true, null]}` are the worker's hand count from the rules above (`10 61 00 01 00 00 00` is `a`; `04 62 00` then the array document `0c 00 00 00 08 30 00 01 0a 31 00 00` is `b`; the top's length `1b 00 00 00` first and a closing `00`: 27 bytes), checked with `python3 -c "import bson; print(bson.encode({'a':1,'b':[True,None]}).hex())"` where `pymongo` is installed - the two must agree. Step 3 also: an array whose first element is named "1" is refused; a length that says 9 for an 8-byte document; a string of length 0. Step 9's negative proof: skip the array-name check when `k != 3`.
* **accept**: ACCEPT-LINUX; ACCEPT-WINDOWS; ACCEPT-CI; `ctest --preset default -R "test_bson|fuzz.seeds"` exit 0; the bson-corpus scores on `tests/conformance/floor.txt` (`bson <valid> <invalid>`), exit 0; the `minimal` preset builds with BSON off.
* **stop if**: as X-1; and a corpus file of a read kind that the model above cannot read to its extended JSON's value (the card is wrong, not the reader: note it).
* **docs**: `CHANGELOG.md` under `## 2.1.0 — unreleased`, `### Added`: "BSON: `CF_WITH_BSON`, reader and writer, held to the MongoDB bson-corpus (D-142)"; `docs/Roadmap.md:168` append "BSON done (X-2)"; `docs/Decisions.md` D-142 with the BSON paragraph; `docs/Formats.md`; `docs/Conformance.md`.

## X-3 - UBJSON

* **id**: X-3
* **goal**: `cf_codec_by_name("ubjson")` reads and writes Universal Binary JSON (Draft 12, ubjson.org), fuzzed, with the specification's examples and a reference library's output as its vectors.
* **why**: as X-1; UBJSON is the binary form that is JSON's own (every type has a JSON twin), so it is the cheapest of the six to hold exactly.
* **needs**: X-2 (it appends to D-142, which X-2 creates)
* **size**: medium
* **version**: 2.5.0
* **status**: open
* **decided**: Names: `CF_WITH_UBJSON`, `ubjson.c`, `cf_codec_ubjson`, `"ubjson"`, `".ubj"`, `test_ubjson.c`, fuzz number 17.
  * **Read**: markers `Z` null, `T` and `F`, `i` int8, `U` uint8, `I` int16, `l` int32, `L` int64 (big-endian), `d` float32, `D` float64, `C` char (one byte below 0x80, read as text of that byte), `S` string (its length is an integer with its marker, then UTF-8), `[` array and `{` object. An object's key is a length (an integer with its marker) and its bytes, no `S`. The optimized containers are read: `$` type with `#` count (`[$U#i5` ...) and `#` count alone. `N` (no-op) is read past wherever a value could begin. `$` without `#` is refused "a container type without a count" (`CF_REASON_SYNTAX`). **Refused by name**: `H` ("a high-precision number, which a configuration has no type for", `CF_REASON_UNSUPPORTED`); a negative length ("a negative length", `CF_REASON_SYNTAX`); a count of items past the bytes left (every item takes a byte); in a `$Z`, `$T` or `$F` container, whose items take no byte, a count past 65536 ("a count of <n>", `CF_REASON_TOO_LONG`). A `$i` array of integers is read as an array of integers.
  * **Top**: an object, then nothing. **Duplicate keys** read, later wins. **Places**: byte offsets. **Detection: none**: an UBJSON document begins with `{` as JSON's does (`detect.c:168`), so it is chosen by name; `test_detect.c` pins that `7b 69 01 61 ...` is not claimed as UBJSON.
  * **Writing**: unoptimized containers with their end markers `]` and `}`, so no count is needed (as CBOR's indefinite lengths). An integer is the smallest of `i`, `U`, `I`, `l`, `L` that holds it; a real is `D` (`d` when exactly a float); a text is `S` with its length as the smallest integer marker; keys as read.
  * **D-142 paragraph** "UBJSON", `Built: X-3`.
  * **Vectors.** The draft's examples, typed into `test_ubjson.c` from `ubjson.org/type-reference/` and `ubjson.org/specification/` (each marker's example bytes and the optimized-container examples); there is no corpus. Reference library: where `py-ubjson` (module `ubjson`) is installed, `conformance.py`'s `ubjson_values` writes one document with `ubjson.dumpb` and with `cf_emit` and compares keys; skipped otherwise.

* **why**: Java services keep configuration in Smile; its shared-name and shared-string tables are what a naive reader gets wrong.
* **needs**: X-3
* **size**: large
* **version**: 2.5.0
* **status**: open

Rejected: writing back-references (the writer would need the tables and nothing needs them).

## X-7 - Property lists, the binary form (bplist00)

* **id**: X-7
* **goal**: `cf_codec_by_name("bplist")` reads Apple's binary property list (`bplist00`) as the JSON model, detects it from its first bytes, is fuzzed, and is documented.
* **why**: `~/Library/Preferences/*.plist` and every app bundle's `Info.plist` are binary plists; the library reads them where it does not read the macOS user defaults (W3-F2c), and a file copied off a Mac is read the same on every platform.
* **needs**: X-6 (D-142's pattern; the wiring list of X-1)
* **size**: large
* **version**: 2.5.0
* **status**: open
* **decided**: Names: `CF_WITH_PLIST` (one option for the binary and the XML form: X-8 adds `plist.c`'s second codec in `plist_xml.c` under the same option), `lib/serialize/src/bplist.c`, `cf_codec_bplist`, `"bplist"`, `".bplist"` only (a `.plist` file may be either form, so `".plist"` belongs to the codec of X-8, which hands a file that begins `bplist00` to this one; `cf_codec_bplist` is registered **after** `cf_codec_plist` in `cf_codecs[]`, `codec.c:61-62`, and X-7 alone, before X-8, has `.plist` unclaimed), `test_bplist.c`, fuzz number 21. Read only (`CF_CODEC_READ | CF_CODEC_TYPED | CF_CODEC_ARRAYS | CF_CODEC_BINARY`): the Roadmap item (`docs/Roadmap.md:171-172`) asks for reading, and writing back is wave 6's.
  * **Layout read.** The header `bplist00` (another version: "a property list version <v>", `CF_REASON_UNSUPPORTED`); the trailer, the last 32 bytes: 5 unused, a sort-version byte (ignored), `offset_size` (1 byte, 1 to 8), `ref_size` (1 byte, 1 to 8), `num_objects`, `top_object`, `offset_table_offset` (each 8 bytes, big-endian). Checked before any object is read: `offset_size` and `ref_size` in 1..8; `num_objects` times `offset_size` fits between `offset_table_offset` and the trailer; every offset read from the table is below `offset_table_offset` and at least 8; `top_object < num_objects` ("a property list with a bad trailer: <what>", `CF_REASON_SYNTAX`).
  * **Objects**, by the marker's high nibble: `00` null, `08` false, `09` true (`0f` fill and any other low nibble: "an unused marker <n>", `CF_REASON_SYNTAX`); `1n` integer of `2^n` bytes (n 0 to 3; n 4, 16 bytes, "an integer past 64 bits signed", `CF_REASON_NUMBER_RANGE`; 8-byte integers are signed, 1, 2 and 4-byte ones unsigned, as the format has them); `2n` real (n 2: 4 bytes, n 3: 8 bytes, big-endian; Infinity and NaN as the text, D-62); `5n` ASCII string (every byte below 0x80 else `CF_REASON_UTF8`); `6n` UTF-16BE string, `n` counting 16-bit units, converted to UTF-8 (a lone surrogate "a string that is not UTF-16", `CF_REASON_UTF8`); `An` array (`n` references of `ref_size` bytes); `Dn` dictionary (`n` key references then `n` value references; every key must be a string, "a key that is a <what>"). Length nibble `f`: an integer object follows with the count. **Refused by name** (`CF_REASON_UNSUPPORTED`, "<kind>, which a configuration has no type for"): `33` date, `4n` data, `8n` UID, `Cn` set.
  * **A graph, not a tree.** Objects reach each other by index. Cycles are caught by the depth counter (`CF_MAX_DEPTH`, "a property list that contains itself", `CF_REASON_DEPTH`); sharing is a DAG and would make a small file expand without bound, so the reader counts every object it reaches and refuses at the count `num_objects + 1` ("more objects reached than the file holds", `CF_REASON_BUDGET`): a tree reaches each at most once, a shared object reaches it twice and the count is exceeded only when the file is hostile or shares nothing useful. (Rejected: a visited bitmap, which needs `num_objects` bits of memory the reader may not have.)
  * **The top** is the dictionary `top_object` names; nothing else is read (an unreachable object is not an error). **Duplicate keys**: read, later wins. **Places**: `<file>, byte <n>`, n the object's offset.
  * **Detection from content: yes.** The 8 bytes `bplist00` with a document of at least 40 bytes (header and trailer), `look_orders` row as Smile's (X-4). `test_detect.c`: a 40-byte file is detected; an INI file whose first line is `bplist00` is not.
  * **D-143**, created by this card in `docs/Decisions.md` after D-142 (`## D-143 — Property lists, binary and XML`): "**Question.** Can a configuration kept as an Apple property list be read as itself? **Decision.** Yes, `CF_WITH_PLIST`, read only: a dictionary at the top, strings, integers, reals, booleans and arrays; dates, data, UIDs and sets refused by name; null (binary form only) is null. The binary form's object graph is read as a tree with a bound of one visit an object, so a shared or self-containing file is refused. Binary detected from `bplist00`; the XML form (D-143, X-8) is read by its own scanner. **Held to.** Apple's own files and `plutil`'s output (X-7's fixtures)." X-8 appends its paragraph.
  * **Vectors.** There is no published corpus. Fixtures: eight `.plist` files made once with `plutil -convert binary1` on a Mac (the XML sources are committed beside them in `tests/fixtures/plist/*.xml`; the binary results are committed as hex in `test_bplist.c` and as files), or, where `plutil` is not available, the Python module `plistlib` (`plistlib.dumps(d, fmt=plistlib.FMT_BINARY)`), which writes `bplist00` as `plutil` does: one document of every kind read, one with a UTF-16 string, one with 300 objects (so `ref_size` and `offset_size` are 2). The reference: `conformance.py`'s `plist_values` (shared with X-8) reads the same dictionary with `plistlib.loads` and compares keys, where Python 3 is installed (it always is: `scripts/` needs it).
* **files**: as X-1 with `bplist` for `msgpack`, without the writer files; `lib/serialize/CMakeLists.txt:33` gets `PLIST:bplist` (and X-8 adds `plist_xml`); `detect.c:168-190`, `test_detect.c`; `tests/fixtures/plist/`.
* **steps**: X-1's steps 1-5, 7-10 (no step 6); step 3 first checks the trailer refusals one by one (each of the five conditions), the graph bound (a self-containing array, a shared child referenced `num_objects` times), a UTF-16 pair, a 16-byte integer. Step 7's floor row `bplist <valid> <invalid>` counts the fixtures and a list `INVALID_BPLIST` (a trailer cut, `offset_size` 0, an offset past the table, a dictionary with an integer key, a cycle). Step 9's negative proof: let the visit count start at 1 when `n != 4`.
* **accept**: X-1's (no writer lists); `detect-bplist`.
* **stop if**: as X-1; `plistlib` and the reader disagree on a fixture and the reader is right by Apple's `CFBinaryPList.c` (note both: the maintainer decides which is the reference).

## X-12 - TLV as the standards have it: DER, SIMPLE-TLV, EMV and KLV

* **id**: X-12
* **goal**: a layout can say `CF_TLV_DER` (the strict form of BER's lengths), `kind = CF_TLV_SIMPLE` (ISO/IEC 7816-4's SIMPLE-TLV), and a test reads EMV's records and SMPTE KLV with them; each is held to documents written by the standard's own examples.
* **why**: D-93 reads BER-TLV and a fixed layout; the standards that sit on top of them differ in small rules (DER's shortest lengths, SIMPLE-TLV's one-byte tags and its 255-escape, KLV's 16-byte keys) that make a reader refuse a good file or accept a bad one.
* **needs**: nothing (`lib/serialize/src/tlv.c` and `test_tlv.c` are in the tree)
* **size**: large
* **version**: 2.5.0
* **status**: parked: not now
* **decided**: What the tree has (D-93, `tlv.c`): `CF_TLV_FIXED` layouts of 1, 2 or 4-byte tags and lengths in either byte order (`tlv_check`, `tlv.c:317-376`) and `CF_TLV_BER`, whose tags are the identifier bytes as one big-endian number up to 4 bytes (`tlv_ber_tag`, `tlv.c:415-448`) and whose lengths are short form or long form of up to 4 bytes, the indefinite length refused (`tlv_ber_len`, `tlv.c:449-491`). `cf_tlv_layout` is a sized struct (`cf_serialize.h:401-414`; `tlv_sized`, `tlv.c:1086-1092`): fields are added only after `ntags`, never inside it, and a layout from an earlier build reads the new fields as zero (D-51, D-93). **No new function; only constants and fields.**

The card adds the test `emv` to `test_tlv.c` reading the file-control information of the payment system directory, `6f 1a 84 0e 31 50 41 59 2e 53 59 53 2e 44 44 46 30 31 a5 08 88 01 01 5f 2d 02 65 6e` (26 bytes inside `6f`: `84` the DF name "1PAY.SYS.DDF01", `a5` the proprietary template holding `88` the SFI 1 and `5f2d` the language preference "en"), with a layout `{6f nest {84 text, a5 nest {88 uint 1, 5f2d text}}}` and its keys `fci.df_name`, `fci.pt.sfi`, `fci.pt.lang`; and a section "EMV" of `docs/Guide.md` showing that layout.   * **DER**: a new flag `CF_TLV_DER = 1u << 3` (add to `known` in `tlv_check`, `tlv.c:318`; "CF_TLV_DER is BER-TLV's" when `kind != CF_TLV_BER`, as `CF_TLV_PADDING`'s check, `tlv.c:355-357`). With it the reader refuses: a length in long form that fits the short form (`81 05`), or has a leading zero byte (`82 00 90`) ("a length that is not the shortest form, which DER does not allow", `CF_REASON_SYNTAX`, in `tlv_ber_len` after `k` is read, `tlv.c:464-478`); a tag whose identifier uses the long form for a number below 31 (`1f 05`), or a long-form tag whose first subsequent byte is `80` ("a tag that is not the shortest form", `CF_REASON_SYNTAX`, in `tlv_ber_tag`); a BOOLEAN-like `bool` tag whose byte is neither `00` nor `ff` ("a boolean that is neither 00 nor FF, which DER does not allow", `CF_REASON_SYNTAX`, in the tag's type `CF_TLV_BOOL` branch). Without the flag BER's looser forms stay read as before. The indefinite length stays refused either way.
  * **SIMPLE-TLV**: a new kind `CF_TLV_SIMPLE = 2` (ISO/IEC 7816-4, 5.4.2): a tag is one byte, `01` to `fe` (`00` and `ff` are refused "a SIMPLE-TLV tag of 00 or FF", `CF_REASON_SYNTAX`; with `CF_TLV_PADDING` they are skipped as BER's are); a length is one byte `00` to `fe`, or `ff` followed by two bytes, big-endian, `0000` to `ffff` (a length below `ff` written in the `ff` form is read, as BER's non-minimal lengths are: SIMPLE-TLV has no strict form, and `CF_TLV_DER` is refused on this kind). The tag's value is the byte (`cf_tlv_tag.tag` = `0x01` to `0xfe`); `tlv_check` accepts the kind and ignores `tag_width`, `length_width` and `order` (they must be 0: "SIMPLE-TLV has no widths to set", `tlv_bad`); `tlv_tag_read` and `tlv_len_read` (`tlv.c:502-540`) get a `CF_TLV_SIMPLE` branch beside the BER one; nesting is the layout's (`CF_TLV_NEST`), as it is for a fixed layout: SIMPLE-TLV has no constructed bit. `tlv_fits` (`tlv.c:123-129`) takes `tag <= 0xfe`.
  * **KLV (SMPTE ST 336): TO DECIDE.** A KLV item is a 16-byte key (a SMPTE universal label, `06 0e 2b 34 ...`), a BER length, the value. `cf_tlv_tag.tag` is a `cf_u32` and cannot name a 16-byte key. Options: (a) a new kind `CF_TLV_KLV = 3` and the key given in the tag's reserved `more` pointer (`cf_serialize.h:394`: "a later 1.x may point it at a sized struct of more, and an earlier library refuses a tag whose `more` is set rather than ignore it", D-51), as `typedef struct cf_tlv_tag_more { size_t size; const unsigned char* key; size_t key_len; } cf_tlv_tag_more;`, matched by `memcmp`, tags searched linearly (a KLV layout has few); (b) key by its last four bytes in `tag` (the first twelve bytes are the SMPTE registry's prefix, `06 0e 2b 34` and the version, and are checked to be that prefix but not told apart): it fits the interface as it is and reads every real KLV file, and it confuses two keys that differ only in the first twelve bytes (the registry allows it); (c) leave KLV out of this milestone. **Recommendation: (a)**: (b) reads wrongly where (a) reads rightly, and (a) is exactly the extension D-51 kept room for. This card does everything else; if (a) is chosen the work is X-12b (`CF_TLV_KLV`, `cf_tlv_tag_more`, `tlv_find` by key, the test with two keys differing at byte 8), written then; the ABI gate has no new symbol either way.
  * **D-147**, created by this card (`## D-147 — TLV as it is met`): "**Question.** What of the TLV that standards and devices use does a layout say? **Decision.** BER, DER (a flag: the shortest forms only) and SIMPLE-TLV (a kind) by a layout; EMV and ISO 7816's records are BER with the padding flag, shown by a test and the Guide, with no code of their own; the layout stays a sized struct that grows only after `ntags` (D-93). KLV waits on the key's representation (X-12b). Fixed layouts' freedoms - the order of the three fields, widths, an implied length, a packed tag and length - are D-147's second paragraph (X-13). **Held to.** `test_tlv`'s standards' examples."
* **files**: `lib/serialize/include/configforge/cf_serialize.h:351-373` (the constants), `lib/serialize/src/tlv.c` (`tlv_check`, `tlv_fits`, `tlv_ber_tag`, `tlv_ber_len`, the type branch of `CF_TLV_BOOL`, `tlv_tag_read`, `tlv_len_read`), `lib/config/tests/test_tlv.c`, `tests/fuzz`'s TLV seeds (`lib/config/tests/test_fuzz.c`: a `fz_ber` seed with a DER-strict layout and a SIMPLE-TLV one, `tests/fuzz/libfuzzer.c:57-60` feeds `fz_tlv()` and `fz_ber()`; add `fz_simple()` as target 26, `all_readers` after `kdl`), `docs/Guide.md` (the EMV section), `docs/Formats.md` (the TLV row: "BER-TLV, DER, SIMPLE-TLV"), `docs/Decisions.md`, `CHANGELOG.md`, `docs/Roadmap.md`, `docs/Codemap.md` and `docs/API.md` (generated; the header comment changed).

## X-13 - TLV as devices write it: field order, widths, an implied length, a packed head

* **id**: X-13
* **goal**: a fixed layout can say the order of its three fields (TLV, LTV or TVL), a tag or length of one to four bytes, a tag whose length is not written, and a tag and a length packed into one byte; each is tested with a document that a device would write.
* **why**: embedded devices save bytes; a `.cfg` of `[len][tag][value]` or of one-byte heads is configuration that today needs code nobody can read (D-93's question).
* **needs**: X-12 (D-147, `tlv.c`'s new branches)
* **size**: large
* **version**: 2.5.0
* **status**: parked: not now
* **decided**: The additions are **fields after `ntags`** in `cf_tlv_layout` (`cf_serialize.h:401-414`; D-51, D-93; `tlv_sized`, `tlv.c:1086`, is unchanged, and `CF_TLV_LAYOUT_INIT` (`:416-418`) gets zeros for them, so every old layout means what it meant). A layout whose `size` ends before a field reads that field as 0.
  * **TO DECIDE (the names).** The interface below is a new public shape no document settles beyond D-93's rule that a layout grows after `ntags`; the maintainer should see it in the card's cold read. **Recommended and used by this card**: after `ntags` in `cf_tlv_layout`: `unsigned field_order; unsigned tag_bits; unsigned length_bits;`; constants `enum { CF_TLV_ORDER_TLV = 0, CF_TLV_ORDER_LTV = 1, CF_TLV_ORDER_TVL = 2 };` (the field order, a name apart from the byte order's `order`), flag `CF_TLV_IMPLIED_LENGTH = 1u << 4`, flag `CF_TLV_TAG_LOW = 1u << 5`. Options: (1) these; (2) a second struct `cf_tlv_layout_more` pointed at by a `more` field (as `cf_tlv_tag.more`): one more indirection for the program, no gain in compatibility since the struct is already sized; (3) refuse the edge cases and ship only wider tags. **Recommendation: (1).** Everything below is decided with it.
  * **Widths**: `tag_width` and `length_width` may be 1, 2, 3 or 4 for a fixed layout (`tlv_check`, `tlv.c:331-342`; the messages become "a tag is 1 to 4 bytes wide, not %u"); `tlv_number` (`tlv.c:403-414`) already reads any width up to 8. `tlv_fits` takes a tag below `2^(8*width)`.
  * **Field order**: `field_order` is `CF_TLV_ORDER_TLV` (0, today's), `CF_TLV_ORDER_LTV` (the length, the tag, the value: `tlv_seq`, `tlv.c:960-1049`, reads length first and then tag; the element's place is still the offset of its first byte) or `CF_TLV_ORDER_TVL` (tag, value, length). TVL cannot be read without knowing how long the value is before the length, so a TVL layout is refused at `cf_tlv_codec` unless **every tag in every table has a nonzero `width` and is `INT`, `UINT`, `BOOL`, `REAL` or `HEX`/`TEXT` with that width** ("TVL needs each tag's width: the length comes after the value", `tlv_bad`): the reader takes `width` bytes as the value and then reads the length, which must equal `width` ("the length says <n>, the tag is <w> wide", `CF_REASON_SYNTAX`). Rejected: reading a TVL stream backward from its end (a different grammar of its own). Not for `CF_TLV_BER` (refused "field order is the fixed layout's").
  * **An implied length**: the flag `CF_TLV_IMPLIED_LENGTH`: a tag whose `width` is nonzero is written with no length field (its value is `width` bytes); a tag whose `width` is 0 has its length written as before. A nest or record with a fixed `width` is read the same way. Refused at `cf_tlv_codec`: the flag on a BER or SIMPLE layout; with `CF_TLV_END_LENGTH` (they contradict). A document that ends inside an implied value: "a value cut short: <n> bytes are left, the tag is <w> wide" (`CF_REASON_TRUNCATED`).
  * **A packed head**: `tag_bits` and `length_bits` both nonzero make one byte hold both: `tag_bits + length_bits` must be 8 ("a packed head is one byte: the bits are %u and %u", `tlv_bad`), the tag in the **high** bits and the length in the low ones by default, or the tag in the low bits with `CF_TLV_TAG_LOW`; then `tag_width` and `length_width` must be 0 and `order` is ignored (refused if set: "a packed head has no byte order"). The length is the number the low bits hold: `0` to `2^length_bits - 1`, with no escape (a value longer than that cannot be written, and a device that needs more uses a wider layout). `kind` stays `CF_TLV_FIXED`. The head read once gives both, so `tlv_tag_read` and `tlv_len_read` (`tlv.c:502-540`) are called through one new `tlv_head_read(s, start, at, end, &tag, &len)`.
  * **D-147's second paragraph**, appended by this card: "**The freedoms of a fixed layout** are fields after `ntags`: `field_order`, widths of 1 to 4 bytes, `CF_TLV_IMPLIED_LENGTH` and a packed one-byte head (`tag_bits`, `length_bits`, `CF_TLV_TAG_LOW`); each is refused at `cf_tlv_codec` where it contradicts another. TVL needs every tag's width."
  * **Documents**, each in `test_tlv.c` as hex: LTV `02 01 aa bb` (the length counts the value only: length 2, tag 01, value `aa bb`); TVL, a tag of width 2 and `length_width` 2, `01 aa bb 00 02`; a 3-byte tag `00 01 02 05 41 42 43 44 45` with a 1-byte length; an implied length layout (`01 aa 02 bb cc` where tag 01 is width 1 and tag 02 width 2); a packed head `4a` with 3 tag bits and 5 length bits is tag 2 and length 10, and with `CF_TLV_TAG_LOW`, 5 tag bits and 3 length bits is tag 10 and length 2; and the refusals above, each with its message and `byte <n>`.
* **files**: `lib/serialize/include/configforge/cf_serialize.h:351-374, 401-418`, `lib/serialize/src/tlv.c` (`tlv_check` `:317-376`, `tlv_fits`, `tlv_tag_read`, `tlv_len_read`, `tlv_seq` `:960-1049`, the new `tlv_head_read`), `lib/config/tests/test_tlv.c`, `lib/config/tests/test_fuzz.c` (a `fz_free()` layout with each freedom, target 27, `libfuzzer.c`, `tests/fuzz/CMakeLists.txt` lists after `simple`), `docs/Guide.md` (a table of the freedoms), `docs/Formats.md`, `docs/Decisions.md`, `CHANGELOG.md`, `docs/Roadmap.md`, `docs/Codemap.md`, `docs/API.md`.
* **steps**: X-12's steps with: step 2 the documents above and every refusal; step 3 see them fail; step 4 widths, then the order, then the implied length, then the packed head, one commit each (`ctest` after each); step 5 the fuzz layout; step 6 the negative proof: let a packed head's `tag_bits + length_bits` be 9 when the layout's name is longer than 6 bytes; see the check's test fail.

## X-14 - Formats bound to a schema: Avro's container, and what the rest waits on

* **id**: X-14
* **goal**: `cf_codec_by_name("avro")` reads an Avro object container file (the specification 1.11, avro.apache.org/docs) whose header carries its schema as JSON, as the JSON model; and the other schema-bound formats are settled as far as they can be without a new public interface, the rest written as TO DECIDE.
* **why**: an Avro file describes itself (it carries its schema), so it needs no new interface; Protobuf, Thrift, FlatBuffers and Cap'n Proto do not, and the question of how a program gives them a schema is the maintainer's.
* **needs**: X-13 (D-147's last word on layouts is not used, but the order keeps `docs/Decisions.md` in one hand); the JSON reader (in the tree)
* **size**: large
* **version**: 2.5.0
* **status**: parked: not now
* **decided**: Names: `CF_WITH_AVRO`, `lib/serialize/src/avro.c`, `cf_codec_avro`, `"avro"`, `".avro"`, `test_avro.c`, fuzz number 28; read only: caps `CF_CODEC_READ | CF_CODEC_TYPED | CF_CODEC_ARRAYS | CF_CODEC_BINARY` and **not** `CF_CODEC_SCHEMA` (D-97: self-describing is the absence of it; the container carries the schema; no built-in codec has SCHEMA, and this keeps it so).
  * **Container read**: the magic `4f 62 6a 01` ("an Avro container begins with Obj and the version 1", `CF_REASON_SYNTAX`); the header's metadata map (a `long` block count, entries of a string key and a bytes value, blocks until a zero count; keys `avro.schema` required, `avro.codec` optional, others ignored); `avro.codec` `null` (or absent) read, any other ("the codec <name>, which needs a decompressor this library does not carry", `CF_REASON_UNSUPPORTED`: deflate, snappy, bzip2, xz and zstandard are refused by name); the 16-byte sync marker; then blocks: a `long` object count, a `long` byte size, the data, the sync marker (a mismatch "a block whose sync marker is not the file's", `CF_REASON_SYNTAX`). A configuration is **one record**: the file must hold exactly one datum over its blocks ("a container of <n> records: a configuration is one", `CF_REASON_STRUCTURE`; none: `CF_REASON_EMPTY`). Counts and sizes are `long` (zigzag varint of up to 10 bytes; an 11th byte or a value past int64 "a number past 64 bits", `CF_REASON_NUMBER_RANGE`; a negative one "a negative size", `CF_REASON_SYNTAX`) and are checked against the bytes left before use.
  * **The schema** is the header's JSON text, read by the library's own JSON reader (`cf_codec_json.decode`) into a private sink that builds a table of at most **256 schema nodes** in the sink's work storage (`reserve_work`; refused "an Avro schema needs sink work storage", `CF_REASON_STORAGE`, as X-4 refuses), each node `{kind, name (offset, length), fields, items, branches}` by index. More than 256: "a schema with more than 256 types" (`CF_REASON_BUDGET`). Named types (record, enum, fixed) are entered by name and may be referred to by name later (a recursive record is legal: the data's depth is bounded by `CF_MAX_DEPTH`, "an Avro value nested deeper than the limit", `CF_REASON_DEPTH`). The top schema must be a `record` ("an Avro file whose top is not a record", `CF_REASON_TOP_LEVEL`).
  * **Datum read** by schema node: `null`; `boolean` (one byte `00` or `01`, else "a boolean of <n>", `CF_REASON_SYNTAX`); `int` and `long` (zigzag varint; an `int` past 32 bits is refused `CF_REASON_NUMBER_RANGE`); `float` and `double` (little-endian IEEE; Infinity and NaN as text, D-62); `string` (a `long` length, UTF-8 checked, handed to the sink in place); `record` a table, `enum` its symbol's text, `array` an array (blocks: a `long` count, negative meaning its absolute value follows a `long` byte size; zero ends), `map` a table (blocks of string-keyed entries, same rule), `union` the branch the leading `long` index names (a `["null", T]` union is null or T; an index past the branches "a union branch <n> of <m>", `CF_REASON_SYNTAX`). **Refused by name** (`CF_REASON_UNSUPPORTED`, "<kind>, which a configuration has no type for"): `bytes` and `fixed`. A logical type is read as its underlying type (`timestamp-millis` is a `long`); a `decimal` is on `bytes` or `fixed` and is refused with them. Field defaults, `doc`, `aliases` and `order` are ignored. Places: `<file>, byte <n>`, n the offset of the datum's first byte.
  * **Duplicate keys** in a map: read, later wins (D-91). **Detection from content: yes**: `4f 62 6a 01` is no text any reader here takes (`01` is a control byte that none accepts at that place): a row in `look_orders` as Smile's (X-4), `detect-avro`.
  * **What is settled for the rest** (D-148): Protobuf (a descriptor set, `FileDescriptorSet`, and the message's full name), Thrift (a struct definition), FlatBuffers (a binary schema, `.bfbs`) and Cap'n Proto (a compiled schema) have **no schema in the bytes**; a program must give one. The library already has the way to give a description at run time: `cf_tlv_codec` makes a codec from a layout the program owns (D-92, D-93: `decode_self` and `data` in `cf_codec`, `cf_serialize.h:221-245`). Nothing in this card adds a public function.
  * **TO DECIDE (how a program gives a schema).** Options: (1) one new function family modelled on `cf_tlv_codec`: `cf_schema_codec(out, kind, bytes, n, message_name, err)` making a `cf_codec` that reads with a binary schema the program holds (Protobuf's descriptor set, FlatBuffers' `.bfbs`, Cap'n Proto's compiled schema, Thrift's JSON-described struct), `kind` an enum, the bytes owned by the program for the codec's life; (2) a per-format function each (`cf_protobuf_codec`, `cf_thrift_codec`, ...): more symbols, each shaped to its format; (3) none: these formats are read through the program's own codec (D-68, a codec from a shared library) and the library's bindings never see them. **Recommendation: (1)**: one shape, one symbol, one place in `gate.abi`, and the sized-struct growth D-93 uses. It is a new public interface before 2.0.0 that adds and breaks nothing, so it may land in 2.1.0; it needs the maintainer's yes before any card is written for Protobuf or the others. This card writes no code for them; when the answer is yes, one card each follows (Protobuf's descriptor reader is the largest: it must read its own wire format, a descriptor set being a message).
  * **D-148**, created by this card (`## D-148 — Formats bound to a schema`): "**Question.** What of Avro, Protobuf, Thrift, FlatBuffers and Cap'n Proto can be read? **Decision.** An Avro container file carries its schema and is read as a self-describing codec (`CF_WITH_AVRO`, one record, no compression, bytes and fixed refused). The others need a schema the program gives; how it gives one is the maintainer's (X-14's TO DECIDE, recommended: one `cf_schema_codec` made as `cf_tlv_codec` is). **Held to.** `test_avro` and the Apache Avro project's own container files."
  * **Vectors.** Apache Avro's `share/test/data/` (github.com/apache/avro, at a pinned commit recorded in `docs/Conformance.md`) holds container files with `null` codec (the worker lists them; `weather.avro` and `weather-deflate.avro` are in it: the deflate one is refused by name, the plain `weather.avro` has several records and is refused by `CF_REASON_STRUCTURE`, both are tested as refusals); the **valid** files are written once by the reference library: where Python's `fastavro` or `avro` is installed, `scripts/check/avro_fixtures.py` (new, ~40 lines) writes the eight fixtures into `tests/fixtures/avro/` (a record of every kind read, an array of records, a nullable union, a recursive record, a map, an enum, a logical type) with the reference writer, and `avro_values` compares the keys read from each with the reference reader's. The fixtures and the script are committed, so no machine needs the package again. Floor `avro-values <n>` and `avro <valid> <invalid>` with `INVALID_AVRO` typed in (a bad magic, a sync marker mismatch, a block size past the file, a union index past the branches, a schema of 257 types, `bytes`).
* **files**: as X-1 for a read-only binary codec with `avro` (fuzz number 28, `detect.c`, `test_detect.c`, `conformance.py`, `floor.txt`), `scripts/check/avro_fixtures.py`, `tests/fixtures/avro/`, `docs/Decisions.md`, `docs/Formats.md` (an "Avro" row and a paragraph under the table on the formats that need a schema), `docs/Dependencies.md` (the fixtures' writer is a development tool).
* **steps**: X-1's steps 1-5 and 7-10 (no step 6); step 3 includes a schema parsed from the header's JSON (every kind, a named type referred to twice, a recursion), the refusals above and the 257-type schema; step 9's negative proof: let the sync marker check pass when the block's count is 3.

## X-21 - Text and binary formats as two groups a build can take apart

* **id**: X-21
* **goal**: `CF_WITH_TEXT_FORMATS` and `CF_WITH_BINARY_FORMATS` are build options that, when OFF, leave out every format of their family, each format's own option still deciding when its family is ON; the profiles and `docs/Limits.md`-style tables say which format is in which family.
* **why**: "the text formats (JSON, YAML, TOML, INI, properties, XML) and the binary ones (CBOR, TLV, blob) as two groups a build can take apart, beside the per-format options" (`docs/Roadmap.md:1029-1031`): an embedded build that reads only binary configuration sets one option, not seven.
* **needs**: X-19 (the files per format are settled)
* **size**: medium
* **version**: 2.2.0
* **status**: parked
* **decided**:
  * **The families.** Text: `INI`, `TOML`, `YAML`, `XML`, `PROPERTIES`, and the text formats of X-9 to X-11 when they exist (`HCL`, `HOCON`, `KDL`). Binary: `CBOR`, `TLV`, and the binary formats of X-1 to X-6 and X-14 (`MSGPACK`, `BSON`, `UBJSON`, `SMILE`, `ION`, `BENCODE`, `AVRO`). **`PLIST` is in neither**: it holds a binary and a text codec (X-7, X-8) under one option, so it stays a per-format option. **`JSON` is in neither**: it stays a per-format option because Report Replay and Doctor read it (`cmake/ConfigForgeOptions.cmake:11-12`: "the JSON and JSON5 codec, which Report Replay and Doctor read"); `COMPOSE`, `REAL`, `DIR`, `DOTENV` and the sources are not formats of a family.
  * **How.** In `cmake/ConfigForgeOptions.cmake`, before the per-format options (`:12-23`), `option(CF_WITH_TEXT_FORMATS "the text formats: INI, TOML, YAML, XML, .properties, and the text codecs after them" ON)` and `option(CF_WITH_BINARY_FORMATS "the binary formats: CBOR, TLV and the codecs after them" ON)`, and each member's `option(...)` becomes `cmake_dependent_option(CF_WITH_<FMT> "<its text>" ON "CF_WITH_<FAMILY>_FORMATS" OFF)` (`include(CMakeDependentOption)`, available from CMake 3.10, the floor `lib/serialize/CMakeLists.txt:8`): with the family OFF the member is forced OFF whatever it was set to and is hidden in the GUI; with it ON it takes the value the user or the profile gave. The two family options are **not** added to `CF_FEATURES` (`:112-130`): they are not features of the library, they are switches over features; `cf_has_feature` is unchanged. The profiles (`cmake/profiles/*.cmake`) that turn members OFF individually keep doing so; `minimal`, `embedded-json` and `embedded-cbor` set the family that applies to ON and the others' members OFF as they do now (the worker checks each profile's result with `cmake -L` before and after: the same `CF_WITH_*` values).
  * **A family OFF with a member that needs the other side**: `PLIST` binary needs nothing of text; `COMPOSE` needs the base codec it wraps (unchanged). `CF_WITH_TEXT_FORMATS=OFF` with `CF_WITH_DOTENV=ON` is fine (dotenv is a source's reader, not a family member); documented.
  * **`docs/Formats.md`** gains a column "Family" in the kind table (`docs/Formats.md:32-41`, "Kind": text or binary is already there: the family is the same word, so no column: **the page says in one sentence that `CF_WITH_TEXT_FORMATS` and `CF_WITH_BINARY_FORMATS` switch those two kinds**). `docs/Guide.md`'s build-options section gets the two options.
  * **The single-file build: TO DECIDE.** Roadmap item: "a generated amalgamation (`configforge_serialize.c`, as SQLite ships), for embedded users who drop one file into their build". `scripts/generate/amalgamate.py` already makes one file for the whole library (`:76`), and `docs/Roadmap.md:1007-1010` records that S-4 left a second amalgamation for the serialization library alone out "for a library nobody asked for alone". Options: (1) a second output `configforge_serialize.c` of `amalgamate.py --only serialize`, gated by `gate.amalgam` like the first; (2) wait until someone asks, as S-4 decided. **Recommendation: (2).** This card therefore adds no amalgamation; if (1) is chosen it is X-21b (the script's `--only`, its test that the output compiles alone with `-DCF_WITH_TEXT_FORMATS=OFF`, the gate).
  * **D-150's fourth paragraph**, appended: "**Families.** `CF_WITH_TEXT_FORMATS` and `CF_WITH_BINARY_FORMATS` force their members OFF when OFF and leave each member's own option when ON; JSON is in neither (the report reads it). The single-file build waits for a user (S-4's decision)."
