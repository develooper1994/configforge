# L - the tools, by group

L-1 to L-8 are done and removed (docs/Plan.md, "Done, their cards removed");
L-3b and L-9, below, are open.

Every kind of tool that finds a fault the others miss, in groups, each with
what the project runs today and what it adds. The rule: a tool joins when it
is free and finds what nothing else here finds; it never replaces one that
works (formatting churn is the cost of a swap, not of an addition). Paid
tools are listed as wished for, not planned: they may never be used.

Where a tool runs: `CI` (a job or step in `.github/workflows`), `verify`
(`scripts/verify.cmake`, a preset or an `EXTRA` step), `planned` (a card
or milestone names it), `new` (a card below).

## L-3b - a sound analyser: Frama-C EVA on the bottom components

* **id**: L-3b
* **goal**: Frama-C's EVA plugin proves, for `lib/port`, `lib/numeric` and `lib/base`, that no execution has an out-of-bounds access, a read of uninitialised memory, a signed overflow, a division by zero or an invalid shift, as `EXTRA=eva` (tier 2) and a CI job `eva`; every alarm is fixed or recorded with its reason.
* **why**: CBMC proves the same classes for inputs up to a bound (`tests/proofs`); EVA proves them for every value of an integer argument by abstract interpretation, and its alarms are the places it could not prove, not a sample. The two disagree usefully: a proof one has and the other lacks is a hole in a harness or in a bound.
* **needs**: L-3; 1.9.0 under way (Maintaining.md: "trusted, on every target" lists the proofs; this is one of them)
* **size**: large
* **decided**:
  * **Frama-C, not IKOS.** IKOS 3.5 (December 2024, the last release) ships no binary (its release has no assets), builds only against LLVM 14, which Ubuntu 26.04 does not package, and speaks LLVM bitcode, so the C89 sources go through clang first. Frama-C 33.0 reads C directly, is on opam, has EVA as a plugin of the one package, and a released version can be pinned. Ubuntu's own `frama-c-base` is the 2022 release and is not in 26.04. Frama-C's licence is LGPL-2.1; it is run, never linked.
  * **Install**: `opam` from apt, `opam init --bare --disable-sandboxing -y`, a switch `cf-eva` with `ocaml-base-compiler.5.3.0` (the version `opam show frama-c.33.0` lists as supported; the worker uses the newest it lists if 5.3.0 is not), `opam install -y frama-c.33.0`. opam checks the checksums its package files carry for each source; the repository itself is pinned: `opam repository set-url default git+https://github.com/ocaml/opam-repository#<the commit the worker records on the day, 40 characters>`. The job caches `~/.opam` with `actions/cache` (pinned by commit like the other actions), key `eva-<frama-c version>-<ocaml version>-<repository commit>`; the first run builds from source and takes 20 to 40 minutes, hence `timeout-minutes: 90`. `setup.sh` installs the same into `/opt/cf-tools/opam`, with `/opt/cf-tools/bin/frama-c` linking to it, only when `FRAMAC=1` is in its environment (it is slow and optional).
  * **Scope**: `lib/port/src/port.c`, `lib/numeric/src/numeric.c`, `lib/base/src/alloc.c`, `error.c`, `key.c`, `value.c`: 2135 lines, the three components at the bottom of D-100's table (`port` uses nothing; `numeric` uses `port` and `lanes`; `base` uses those and `numeric`), whose callers are everyone else. `lanes` is not in it (its portable and vector files are a different analysis). The next card extends it upward.
  * **How it runs**: one harness per component, `tests/eva/eva_<component>.c` (new), each calling every function the component's headers export under `CF_INTERNAL_API=1` with arguments from Frama-C's builtins (`Frama_C_interval`, from `__fc_builtin.h`): integers in their whole range, a pointer to a stack buffer of a fixed size (64 bytes) with a length in `0..64`, the string arguments NUL-terminated at an unknown place. `scripts/check/eva.cmake -DSRC= -DSTAGED=` (new) runs, for each harness, `frama-c -cpp-extra-args="-I<staged> -DCF_INTERNAL_API=1" -machdep gcc_x86_64 -eva -eva-precision 3 -eva-slevel-function <fn>:<n> where a loop needs it -warn-signed-overflow -warn-invalid-shift -eva-warn-copy-indeterminate -then -report -report-csv <out>.csv -no-unicode` and reads the CSV. Unsigned wrap is not an alarm (C defines it, and the code uses it on purpose); a signed overflow is. Flag spellings are confirmed against `frama-c -help` of 33.0; a renamed flag is a step-order question, not a design one.
  * **What it must prove**: no property of status `Unknown` or `Invalid` among the kinds `mem_access`, `index_bound`, `initialization`, `signed_overflow`, `division_by_zero`, `shift`, `pointer_arithmetic`, `valid_pointer` for any line of the six files.
  * **Triage, in this order, for each alarm**: (1) it is a fault: fix the code, with a test in `lib/<component>/tests` that fails before (the regression, as the fuzzers' findings get); (2) the analysis is too coarse: raise `-eva-slevel-function` for that function (never above 500, never a global `-eva-slevel`), or split the harness's range; (3) it holds for a reason Frama-C cannot see: a line in `.eva-accepted.txt` (new, at the root): a `#` line with the reason, then `<file> <function> <kind>`; never a whole file. `scripts/check/eva.cmake` fails on an alarm not listed and on a listed entry no alarm matches.
  * **EXTRA step and CI job**: `EXTRA=eva` (tier 2; in the `TIER=2` list, the usage comment and the unknown-step message), skipped with `eva                   skipped: no frama-c` when `find_program(FRAMAC_EXE frama-c HINTS /opt/cf-tools/bin)` finds none; steps `eva configure` (the default preset's configure, for the staged headers), `eva run`. CI job `eva` as above, on every push to `main` and on pull requests that touch `lib/port`, `lib/numeric`, `lib/base`, `tests/eva`, `.eva-accepted.txt` or the job (its first step is `git diff --name-only` against the push's base; when none of those paths changed the job ends green at once, with no action from outside the repository), so the cached switch's 20 minutes are not paid on a documentation commit.
  * **Stop numbers**: more than 30 distinct alarms on the first pass after step 4's precision work; the install not reproducible twice from the pinned repository commit; one function whose alarm needs `-eva-slevel-function` above 500.
* **files**: `tests/eva/eva_port.c`, `eva_numeric.c`, `eva_base.c`, `scripts/check/eva.cmake`, `.eva-accepted.txt`, `scripts/verify.cmake` (`eva`), `scripts/buildenv/setup.sh`, `.github/workflows/ci.yml` (job `eva`), the sources and tests the alarms lead to; last: `docs/Safety.md` (a paragraph beside the CBMC one: what each proves, and that `.eva-accepted.txt` is the list of what is trusted), `docs/Dependencies.md` (a row: `Frama-C 33.0 (opam; LGPL-2.1-only) | `EXTRA=eva` (tier 2) and the CI job `eva`: EVA over `port`, `numeric` and `base` (`tests/eva`, `.eva-accepted.txt`); not linked` and one for `opam`), `docs/plan/L-tools.md` (group 4 "Today"), `CHANGELOG.md`.
* **steps**:
  1. `git switch -c work/L-3b`. Install Frama-C locally as above (WSL, off `/mnt`); record the opam repository commit.
  2. Write `tests/eva/eva_port.c` first, with one function of `port.c`; run `frama-c` by hand; see the CSV list its alarms. Then every exported function of the component; then `eva_numeric.c`, `eva_base.c`.
  3. `scripts/check/eva.cmake` and `EXTRA=eva`. See it fail: the first pass lists every alarm and exits 1. More than 30 distinct after precision work: stop.
  4. Triage each alarm as decided. See the fix of a real one demonstrated: revert the fix, see the alarm return and the new test fail, restore.
  5. The CI job `eva` and `setup.sh`'s `FRAMAC=1` branch; push the branch; the first run is the slow one, the second (from the cache) must take under 10 minutes.
  6. `docs/Safety.md`, `docs/Dependencies.md`, `docs/plan/L-tools.md`, `CHANGELOG.md`.
  7. ACCEPT.
* **accept**: ACCEPT-LINUX, ACCEPT-CI with `eva` green twice running (the second from the cache); `cmake -DEXTRA="eva;proofs" -DMODE=quick -DJOBS=3 -P scripts/verify.cmake` ending `all green`.
* **stop if**: a stop number above; an alarm that is a real fault needing a change to a public signature or limit (record it as accepted with the reason, write it under "notes", tell the maintainer); Frama-C 33.0 not installable from the pinned repository commit on the runner.
* **notes**: (empty)

## L-9 - the OpenSSF Scorecard findings the project can fix itself

* **id**: L-9
* **goal**: the repository's code-scanning alerts of the tool Scorecard that a commit can fix are fixed: DangerousWorkflow (`bench.yml`), PinnedDependencies (five pip installs and one container image), SecurityPolicy (`SECURITY.md` has no link); the rest are listed under "notes" for the maintainer.
* **why**: the first is a real risk, the other two cost nothing. `bench.yml`'s job `history` runs on `workflow_run` of `ci`, which holds the base repository's token (`contents: write`), and its checkout takes `ref: ${{ github.event.workflow_run.head_sha }}`: the code of the run that triggered it. If that run is ever one a stranger controls (a pull request from a fork, a branch), their `scripts/bench/page.py` and `publish.sh` run with the write token. Today the job's `if` limits it to a push on `main`, but a guard that the next edit can drop is a weaker thing than a job that never checks out foreign code.
* **needs**: L-2 (the gates `gate.actionlint` and `gate.shellcheck`)
* **size**: small
* **decided**:
  * **DangerousWorkflow**: the privileged job checks out nothing but the default branch's tip (no `ref:`: a `workflow_run`'s GITHUB_SHA), so every script it runs is what is on `main` now. What the unprivileged run made is *data*: one JSON file (the artifact `bench-quick`), read by `page.py --validate` and `publish.sh`, never executed, never put in a shell line. `if:` also requires `head_branch == 'main'` and `head_repository.full_name == github.repository`. `permissions` stay as they are (`contents: write`, `actions: read` for this job alone, `contents: read` for the file): the job's purpose, adding a file to the branch `bench-history`, needs exactly them. The job's purpose does not need the pull request's code, so nothing moves into `ci.yml`. Pushes to `main` and the schedule behave as before.
  * **The data is validated as untrusted**: `publish.sh` makes a path (`runs/<year>/<committed_at>-<sha7>-<kind>.json`) and a commit message from the file's fields, so `page.py --validate` must accept exactly what `run.py` writes: `committed_at` as `YYYY-MM-DDThh:mm:ssZ`, `run_id` digits, `compiler.id` `gcc` or `clang`, `compiler.flags` `shipped`, `bare` or `native`, `cells` a list. New `scripts/bench/test_page.py` (run by `bench-gate` beside `test_gate.py`); it fails before the change on the first three of its refusals.
  * **PinnedDependencies, pip**: every `pip install` in `scripts/buildenv/setup.sh` and `dev-setup.sh` is `pip install --require-hashes --no-deps -r <list>`, the lists made by `scripts/buildenv/requirements-lock.py` from `<name>.in` as L-3 made the semgrep one (the script, `semgrep.in` and `semgrep-requirements.txt` move from `scripts/check/` to `scripts/buildenv/`, so that the Containerfile, whose context is that directory, can copy them): `tools` (clang-format, json5, shellcheck-py, ruff, actionlint-py, codespell), `semgrep`, `cmakelang` (macOS; with `six`). `setup.sh` installs a list again when a line of it is not what `pip list` holds; the versions are the ones it pinned before (a version that changes is a change of a `.in` file and a new lock). CI's job `lint` installs the `tools` list with the `semgrep` one, so the two cannot differ. `dev-setup.ps1`'s `pip install --user` (Windows, a tool name from a list) is not in the alerts and stays.
  * **PinnedDependencies, image**: `.clusterfuzzlite/Dockerfile` names `gcr.io/oss-fuzz-base/base-builder@sha256:<digest>` (the manifest digest the registry returns for `latest` on the day); Dependabot's `docker` ecosystem on `/.clusterfuzzlite` proposes the next digest. If the digest cannot be read, the line goes under "notes" for the manager, who has `gh`.
  * **SecurityPolicy**: `SECURITY.md` states how to report (the link `https://github.com/develooper1994/configforge/security/advisories/new`), the supported versions (the latest minor of the current major, and `main`), and the response times as a best effort of one maintainer.
  * **Left to the maintainer** (settings or time, not files): BranchProtection, CodeReview, CIIBestPractices (the badge programme), Maintained.

## L-10 - supply-chain hardening, the parts the project can do itself

* **id**: L-10
* **goal**: no code reaches a build of this repository unpinned and unseen: every download in a workflow or a script is listed with how it is held (a commit or a SHA-256) and a gate fails on one that is not; pull requests that add a vulnerable or copyleft-licensed dependency fail; every workflow's top-level token is read-only, held by a gate; and each release carries its SBOM as a file of its own, attested like the archives.
* **why**: the maintainer, 2026-11-24: supply-chain attacks are frequent, and none should reach the project. Already in place, not redone here: actions pinned by commit; tool downloads in CI checked by SHA-256; pip installs and the fuzz image pinned by hash, and no privileged `workflow_run` that runs foreign code (L-9); osv-scanner and gitleaks in CI; build provenance for every published file (`actions/attest-build-provenance` in `release.yml`, `gh attestation verify` in the README); SHA256SUMS; the musl archive built twice and compared (N-2); Scorecard. What is left is what no gate holds yet: the next edit can add an unpinned `curl` or a workflow with a write token and nothing fails. One hole is open today: the job `vcpkg` in `ci.yml` clones vcpkg's moving `HEAD` (`ci.yml:242`) and runs its bootstrap.
* **needs**: L-9 (done)
* **size**: medium
* **decided**:
  * **vcpkg pinned**: `ci.yml`'s `vcpkg` job takes a fixed commit: `git init "$RUNNER_TEMP/vcpkg"`, `git -C ... fetch --depth 1 https://github.com/microsoft/vcpkg.git <40-hex>`, `git -C ... checkout FETCH_HEAD`, the commit being the tip of `microsoft/vcpkg`'s `master` on the day (`gh api repos/microsoft/vcpkg/commits/master --jq .sha`), with a comment `# vcpkg master on <date>; moved by hand`.
  * **The fetch inventory**, `scripts/check/fetches.txt`: one line a fetch, three tab-separated fields: the file (repository path); a URL prefix as written in that file, up to the first `$`, `"` or space; and how it is held: `sha256 <where the hash is checked>`, `commit <40-hex, or where it is>`, or `data <why no code runs from it>` (musl's COPYRIGHT text is `data`). `#` lines and empty lines are ignored. Every fetch line of the tree is covered by exactly one entry; an entry no line matches fails too.
  * **`gate.fetches`**: `scripts/check/fetches.py` (Python 3 standard library only, like `check_text.py`), registered as a ctest test exactly where and how `gate.text` is (`git grep -n "gate.text" -- cmake CMakeLists.txt`). It takes the tracked files (`git ls-files`) under `.github/`, `scripts/`, `cmake/`, `bench/`, `packaging/`, and `CMakeLists.txt` files anywhere, and matches each line against `FetchContent_Declare|ExternalProject_Add|git clone|git fetch|curl -|wget |file\(DOWNLOAD|Invoke-WebRequest|iwr ` (not `docs/`, not `*.md`, not C sources: `tools/doctor/spring.c`'s comment is not a fetch; `fetches.txt` and `fetches.py` themselves are skipped). For each line it finds the entry whose file is the line's file and whose prefix occurs in the line; a line in a file with no URL on it (e.g. `git fetch` of a variable) matches an entry whose prefix is `-` for that file. Output: `fetches: <file>:<line>: not in scripts/check/fetches.txt` or `fetches: <entry line>: no such fetch`, exit 1; otherwise `fetches: <n> held`, exit 0. It does not prove the hash is checked: the third field is for the reviewer; the gate makes sure no fetch is added unseen.
  * **`gate.permissions`**: `scripts/check/permissions.py` (standard library), registered as `gate.fetches` is. For every `.github/workflows/*.yml`: a top-level `permissions:` (column 0) exists; it is `permissions: {}` or is followed by indented `<scope>: read` or `<scope>: none` lines only; `read-all`, `write-all` and any `write` at the top fail, naming the file and line. Job-level blocks are not checked (a job asks for what it needs). `scorecard.yml`'s top-level `permissions: read-all` becomes `permissions:` with `  contents: read`; its job keeps its own block (`security-events: write`, `id-token: write`, `contents: read`, `actions: read`), which is what the Scorecard action asks for.
  * **Dependency review**: a new `.github/workflows/dependency-review.yml`: `on: pull_request`, top-level `permissions:` / `  contents: read`, one job on the runner image `scorecard.yml` uses, `actions/checkout` at the commit the repository already pins, then `actions/dependency-review-action@<40-hex> # v<tag>` (the latest release: `gh api repos/actions/dependency-review-action/releases/latest --jq .tag_name`, then that tag's commit, peeled), with `fail-on-severity: moderate` and `deny-licenses: GPL-2.0-only, GPL-3.0-only, AGPL-3.0-only` (the project is zlib-licensed; copyleft in a dependency would bind its users). Not a required check: the maintainer makes it one in the repository's settings. It needs GitHub's dependency graph, on by default for a public repository; if the first run says it is off, the job stays and the setting goes under notes.
  * **The SBOM as a release file**: in `release.yml`'s `linux-musl` job, after `cp "$work/a/$archive" dist/`: `find "$work/a/stage" -name configforge.spdx.json` must give exactly one file (otherwise `exit 1`), copied to `dist/configforge-$v-linux-x86_64-musl.spdx.json`. It is uploaded with the archive, attested by the existing step (`subject-path: "dist/*"`) and listed in SHA256SUMS; `publish` does not change. The header comment's list of published files gains the line. README.md:441's paragraph gains one sentence: the Linux archive's SBOM is published beside it and verified the same way.
  * **Not here** (each needs an account, a key, a token or a setting: the maintainer's; under notes and in HANDOFF.md): a ruleset on `main` (required reviews, required status checks); signed commits and tags; two-factor authentication; trusted publishing for PyPI and crates.io; the dependency graph if it is off.
* **files**: `.github/workflows/ci.yml` (the `vcpkg` job), `.github/workflows/scorecard.yml` (top-level permissions), `.github/workflows/dependency-review.yml` (new), `.github/workflows/release.yml` (the `linux-musl` job, the header comment), `scripts/check/fetches.py`, `scripts/check/fetches.txt`, `scripts/check/permissions.py` (new), the CMake file where `gate.text` is registered, `README.md` (one sentence), `docs/Dependencies.md` (a short section "Fetches": the inventory and the gate), `SECURITY.md` (one line: how a user verifies an archive and its SBOM), `scripts/README.md` (the two scripts), `docs/Plan.md`, this card. No `CHANGELOG.md` entry: CI and scripts only.
