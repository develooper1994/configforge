# L - the tools, by group

Every kind of tool that finds a fault the others miss, in groups, each with
what the project runs today and what it adds. The rule: a tool joins when it
is free and finds what nothing else here finds; it never replaces one that
works (formatting churn is the cost of a swap, not of an addition). Paid
tools are listed as wished for, not planned: they may never be used.

Where a tool runs: `CI` (a job or step in `.github/workflows`), `verify`
(`scripts/verify.cmake`, a preset or an `EXTRA` step), `planned` (a card
or milestone names it), `new` (a card below).

## L-1 - the other languages' linters

* **id**: L-1
* **goal**: shellcheck, ruff, actionlint and codespell run in `verify` and CI, and the tree passes them.
* **why**: the scripts that land every card, the Python binding and the workflows had no checker; two faults in `scripts/work` on 2026-11-19 were of shellcheck's kind.
* **needs**: 1.7.0 released
* **size**: medium
* **decided**: each tool a gate test (`gate.shellcheck`, `gate.ruff`, `gate.actionlint`, `gate.codespell`) beside `gate.format.cmake`, skipped with a message when the tool is absent, as the format gates are; `setup.sh` and `dev-setup` install them; the first pass fixes what they find, or records a reasoned exception in the tool's own config file (`.shellcheckrc`, `pyproject.toml [tool.ruff]`, `.codespellrc`).
* **accept**: ACCEPT-LINUX, ACCEPT-CI.

## L-2 - run-time, fuzzing and supply chain in CI

* **id**: L-2
* **goal**: Valgrind's memcheck, AFL++ on the libFuzzer targets, gitleaks, osv-scanner and OpenSSF Scorecard run in CI; and every sanitizer a compiler offers for C on the CI's targets runs: MemorySanitizer (a clang preset `msan`), clang's extra UBSan groups (`integer`, `implicit-conversion`, `nullability`, `local-bounds`; a clang preset `ubsan-strict`), and the run-time options that make a finding fatal and look further in the presets' test environment. HWASan comes with the Arm CI (1.9.0).
* **why**: the sanitize preset reads what ASan, LSan and UBSan's default checks see, on GCC and MSVC; a read of memory nobody wrote (MSan, Valgrind), a narrowing that loses a value (`implicit-conversion`) and an input only a second fuzzer's mutations reach (AFL++) are seen by none of them. A leaked secret or a vulnerable pinned dependency, and a repository whose practices nobody outside has measured, are faults no test can show.
* **needs**: L-1 (done, 7bec7d8)
* **size**: medium
* **decided**:
  * **Where each runs.** `EXTRA` steps of `scripts/verify.cmake`: `valgrind` (exists), `msan`, `ubsan-strict`, `afl` (new; each skipped with a message where its tool is absent, as every EXTRA is; the three new ones join `TIER=2`). CI jobs in `ci.yml`: `valgrind`, `msan`, `ubsan-strict`, `afl`, `secrets`, `osv`; Scorecard in a workflow of its own, `scorecard.yml` (its permissions and allowed steps differ). Every action by commit SHA with its tag after it, as the existing ones are. gitleaks and osv-scanner are CI jobs only, and `setup.sh` installs them so the maintainer can run them by hand: osv-scanner needs the network, and a scan of the whole history is not a gate in verify.
  * **Valgrind.** The step exists (`EXTRA=valgrind`: every `^unit\.` test, `--leak-check=full --errors-for-leak-kinds=definite --track-origins=yes`, `--error-exitcode=99`). Job `valgrind` (ubuntu-26.04, `timeout-minutes: 60`): `sudo apt-get update && sudo apt-get install -y valgrind`, then `cmake -DEXTRA=valgrind -DMODE=quick -DJOBS=4 -P scripts/verify.cmake`. A finding is fixed in the library or the test; a false report of glibc's or the kernel's goes into `tests/valgrind.supp` (new, only if needed; passed as `--suppressions=<file>` by the wrapper `verify.cmake` writes, only when the file exists), each entry preceded by a `#` line with its reason.
  * **MemorySanitizer** (`-DCF_SANITIZE_MEMORY=ON`, a new option in `cmake/ConfigForgeAnalysis.cmake` beside `CF_SANITIZE_THREAD`): `-fsanitize=memory -fsanitize-memory-track-origins=2 -fno-omit-frame-pointer -fno-sanitize-recover=all -g`, compile and link. Clang only (`FATAL_ERROR "CF_SANITIZE_MEMORY needs clang"` otherwise); it excludes `CF_SANITIZE`, `CF_SANITIZE_THREAD` and `CF_FUZZ` (a `FATAL_ERROR` for each, worded as the existing pair); it joins `CF_INSTRUMENTED`. **The preset `msan` builds the library and its tests with no optional external dependency**: `CF_WITH_XML`, `CF_WITH_YAML`, `CF_WITH_SQLITE` and `CF_WITH_CXX` OFF. Why: MSan tracks "initialised" in shadow memory, and a library not built with it (expat, libyaml, libfyaml, sqlite, libstdc++) writes memory the shadow never learns of, so every value it hands back reads as uninitialised: a flood of reports that are not faults. glibc is the exception, which MSan handles itself with interceptors for the calls it knows. Those formats are read by the `yaml` job and by `EXTRA=yaml`; MSan does not cover them, and `docs/Dependencies.md` says so. The preset: `Debug`, compiler `clang`, `binaryDir` `build-msan`. A report that is glibc's and not the library's (a libc function with no interceptor) is not fixed in the library: the test is labelled `no-msan` where it is defined (`set_property(TEST <name> APPEND PROPERTY LABELS no-msan)`, the reason in a comment on the line above), and the `msan` test preset excludes that label (`"filter": {"exclude": {"label": "no-msan"}}`).
  * **Extra UBSan groups** (`-DCF_SANITIZE_STRICT=ON`, a new option; needs `CF_SANITIZE=ON` and clang, a `FATAL_ERROR` otherwise): added to what `CF_SANITIZE` already passes, `-fsanitize=integer,implicit-conversion,nullability,local-bounds` and `-fsanitize-ignorelist=${CMAKE_SOURCE_DIR}/.ubsan-ignorelist.txt`, compile only. The preset `ubsan-strict`: `CF_SANITIZE` and `CF_SANITIZE_STRICT` ON, clang, `Debug`, `binaryDir` `build-ubsan-strict`. `-fno-sanitize-recover=all` stays, so a finding fails its test. **How the findings are met.** `implicit-conversion` and `integer` (which includes `unsigned-integer-overflow`) report every narrowing and every wrap, the intentional ones among them (hash arithmetic wraps on purpose; a byte is taken from an `int` on purpose). The first pass reads each distinct site (file and line) and does one of two things: fixes it (an explicit cast with the range reasoned in a comment, or a wider type, or the check that makes it safe), or, when the narrowing or wrap is what the code means (hashing, checksums, bit packing), lists it in `.ubsan-ignorelist.txt` (new, at the root; clang's `-fsanitize-ignorelist=` format): a `#` line with the reason, then `fun:<name>` for one function or `src:<path glob>` for one file, under a section naming the check (`[implicit-signed-integer-truncation]`, `[unsigned-integer-overflow]`, ...), never a bare `src:` for a whole library. An entry has the narrowest scope that silences it. The count of distinct sites is the card's own stop (below).
  * **Fatal and wider run-time options**, as `"environment"` of the `sanitize`, `ubsan-strict` and `msan` **test presets** in `CMakePresets.json` (verify and CI run through `ctest --preset`, so this reaches every run): `sanitize` and `ubsan-strict` get `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1` and `ASAN_OPTIONS=detect_stack_use_after_return=1:strict_string_checks=1:detect_invalid_pointer_pairs=2:check_initialization_order=1`; `msan` gets `MSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`. (`-fno-sanitize-recover=all` already makes UBSan's findings fatal at compile time; the option says it again where a build forgets, and prints the stack.) The `fuzz` and `tsan` presets are not touched. These options reach GCC's and MSVC's `sanitize` runs too; if MSVC's AddressSanitizer refuses one of the four ASan flags, that is a "stop if", not a reason to drop the option elsewhere.
  * **ASLR.** MSan, like TSan (`ci.yml` job `tsan`; `verify.cmake` `EXTRA=tsan`), maps its shadow at fixed addresses and fails on a kernel that randomises mmap with more bits than the runtime expects. The `msan` job and the `msan` step therefore run the tests as the `tsan` ones do, `setarch "$(uname -m)" -R ctest --preset msan`. Harmless where it is not needed.
  * **AFL++ on the libFuzzer harnesses.** The harnesses in `tests/fuzz` (`libfuzzer.c`, `chain.c`) are reused as they are, and no source changes: AFL++'s compiler wrapper `afl-clang-fast`, given `-fsanitize=fuzzer` (which `tests/fuzz/CMakeLists.txt` already passes), links `libAFLDriver.a`, AFL++'s own `main` that calls `LLVMFuzzerTestOneInput`, in place of libFuzzer's; the program then reads one input from the file named on its command line (`@@` in `afl-fuzz`) or from stdin. The preset `afl`: `CMAKE_C_COMPILER=afl-clang-fast`, `CMAKE_CXX_COMPILER=afl-clang-fast++`, `CMAKE_BUILD_TYPE=RelWithDebInfo`, `CF_FUZZ=ON`, `CF_WITH_CXX=OFF`, `binaryDir` `build-afl`; `CF_FUZZ` already asks `-fsanitize=address,undefined` of every target. (`CF_FUZZ` demands a compiler id that matches Clang; `afl-clang-fast` wraps clang and should report it: if CMake's id for it is not Clang, the preset's configure fails, which is a "stop if".) **Driver**: `scripts/check/afl.cmake` (new), `cmake -DBUILD=build-afl -DSECONDS=<n> -P scripts/check/afl.cmake`. It runs `fuzz_seeds` once (`build-afl/tests/fuzz/fuzz_seeds`, which writes `seed_<reader>/` where it runs, as the `fuzz.*` tests read them), then for each `fuzz_<reader>` the build made (`fuzz_seeds` excluded) `afl-fuzz -V <n> -m none -i <seeds> -o build-afl/afl-out/<reader> -- ./fuzz_<reader> @@`, with `AFL_NO_UI=1 AFL_SKIP_CPUFREQ=1 AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1 AFL_FORKSRV_INIT_TMOUT=10000` in the environment (a runner has no `core_pattern` to set and no frequency governor to change). `fuzz_chain`'s seeds are the three `fuzz_chain_seed*` files, copied into a directory of their own. AFL++ refuses an empty seed directory: a reader with none is a fatal error of the script. After each target, any file named `id:*` in `<out>/<reader>/default/crashes/` fails the script, which prints the names and leaves the directory. **Duration**: `n` is verify's `FUZZ_SECONDS`, **60 in CI as the `libfuzzer` job's is**, per target, one after the other (so the job takes about as long as `libfuzzer`; afl-fuzz binds a core and a runner has few); verify's default is 10 as `fuzz`'s is. The corpus is not cached between runs in this card (`libfuzzer` caches its own). The `EXTRA` step `afl` (skipped with a message where `afl-clang-fast` or `afl-fuzz` is absent, and on Windows) configures `--preset afl`, builds it, and runs the driver. The CI job `afl` (ubuntu-26.04): `sudo apt-get update && sudo apt-get install -y afl++ clang llvm`, then `cmake -DEXTRA=afl -DFUZZ_SECONDS=60 -DMODE=quick -DJOBS=4 -P scripts/verify.cmake`; on failure it uploads `build-afl/afl-out` as the artifact `afl-findings`, as `libfuzzer` does its crashes. Ubuntu's `afl++` package is the pin (as `iwyu`'s package is: the image CI runs on); `docs/Dependencies.md` names the version the first green run printed. If the package's clang plugin does not match clang 21 (`afl-cc` reports a version mismatch), that is a "stop if".
  * **gitleaks**: job `secrets` on every push and pull request: `actions/checkout` with `fetch-depth: 0`, then the release binary, pinned by version and checked against the SHA-256 the release publishes (as lychee is in job `lint`; the same two values go into `setup.sh`), `gitleaks git --no-banner --redact --exit-code 1 .`: every commit, the secret itself never printed. `.gitleaks.toml` (new, at the root): `[extend] useDefault = true` and an `[allowlist]` for what the first pass shows is no secret (a test's fixed key, a digest in a document), each entry with a `description` giving its reason and a path or `regexes` as narrow as possible. A finding that is a real secret: **stop and tell the maintainer** (it must be revoked, not allowlisted).
  * **osv-scanner**: job `osv` on every push and pull request, the release binary pinned and checked as above (v2: `osv-scanner scan source`), reading **the two lockfiles the tree has**: `bindings/rust/Cargo.lock` and `scripts/docs/requirements.txt` (the documentation's pinned Python packages). Nothing else is a lockfile here: `packaging/vcpkg/configforge/vcpkg.json`, `conanfile.py` and `pyproject.toml` pin no versions of their own, and the library has no dependency (`docs/Dependencies.md`). Command: `osv-scanner scan source --lockfile=bindings/rust/Cargo.lock --lockfile=scripts/docs/requirements.txt` (if the pinned version spells the flag differently, that version's `osv-scanner scan source --help` is the judge). A vulnerability in a pin is fixed by raising the pin; one with no fixed version available goes into `osv-scanner.toml` (new, at the root, an `[[IgnoredVulns]]` with `id`, `ignoreUntil` three months out and `reason`), never silently.
  * **OpenSSF Scorecard**: `.github/workflows/scorecard.yml` (new): `on:` `schedule` (cron `23 4 * * 2`, Tuesdays), `push` to `main`, `branch_protection_rule`, `workflow_dispatch`; top-level `permissions: read-all`; one job `analysis` with `permissions: security-events: write, id-token: write, contents: read, actions: read`; steps: `actions/checkout` (`persist-credentials: false`), `ossf/scorecard-action` (`results_file: results.sarif`, `results_format: sarif`, `publish_results: true`), `actions/upload-artifact` (`results.sarif`, `retention-days: 5`) and `github/codeql-action/upload-sarif` (`sarif_file: results.sarif`). **No secret is needed**: with `publish_results: true` the action authenticates to the Scorecard service with the job's OIDC token (`id-token: write`) and reads the repository with the default `GITHUB_TOKEN`; no `repo_token` is passed. (The one check that wants more, Branch-Protection, reads as unknown without a token of admin scope; accepted, and a personal access token is the maintainer's to give, not this card's.) The workflow has no `run:` step and uses no action but those four: `publish_results` refuses a workflow that does. **The result on the docs site** is the badge in `README.md`, which is the docs site's Home page (`mkdocs.yml`, `nav: Home`; there is no `docs/index.md`): `[![OpenSSF Scorecard](https://api.scorecard.dev/projects/github.com/develooper1994/configforge/badge)](https://scorecard.dev/viewer/?uri=github.com/develooper1994/configforge)`, on its own line under the opening sentence, linking to the public result. The badge shows a score only after the workflow's first run on `main`; the card is accepted without it (CI cannot show it before the push to `main`), and the CHANGELOG bullet says so.
  * **Rejected**: gitleaks as a ctest gate (history and a binary on every machine; CI's job is the judge); MSan with the optional libraries built from source in the job (a day of work for formats the `yaml` job covers); AFL++ through the `fuzz` ctest preset (the tests' arguments are libFuzzer's); a `repo_token` for Scorecard.
