## N-19 - `gate.misra`: cppcheck's MISRA addon on the `misra` profile, with a record for every report

* **id**: N-19
* **goal**: `ctest --preset misra -R gate.misra` runs cppcheck's MISRA C:2012 addon over the library sources the `misra` profile builds and fails on a report that `docs/compliance/deviations.txt` does not hold, and on a record line that matches no report or a different number of them; the file holds every report of the first run, each with a kind and a reason; and the gate runs in CI.
* **why**: The Roadmap's "`gate.misra` on the `misra` profile" (Next after 1.8.0, item 6) is what is left of the first step of "Critical-system standards": N-9 and N-10 put cppcheck on both libraries and A-11 made the profile, so the claim "checked against MISRA C:2012 on every commit" (`docs/Compliance.md:194`) has no check behind it. A count that cannot rise is what keeps a safety claim true while the library changes, and each later card that fixes a rule has to lower a line: that is the ratchet. Nothing here says "compliant": the page's words stay "follows, with a free checker" until a qualified tool has run (`docs/Compliance.md:138-146`).
* **needs**: nothing (A-11, N-9 and N-10 are done)
* **size**: medium
* **decided**:
  * **What is run, and over what.** `cppcheck --project=<build>/compile_commands.json --file-filter=*/lib/*/src/* --std=c89 <compiler defines> --enable=style --addon=misra --cppcheck-build-dir=<build>/misra-cppcheck -j <jobs> --template={file}:{line}:{column}: {id} --suppress=missingIncludeSystem --suppress=unusedFunction --quiet`, working directory the source root, in the build of the `misra` preset (`CMakeLists.txt:58` already writes `compile_commands.json`). `--project` gives cppcheck the profile's own `-D` set (`CF_WITH_REAL=0`, `LANES_SCALAR_ONLY=1`, ...), so the one configuration the profile compiles is the one analysed, not every `#ifdef`. The filter is the library's sources, `lib/<part>/src/` at any depth; `lib/*/tests/`, `tests/` and `tools/` are not the library (`docs/Compliance.md:29` scopes the standard to `lib/`). Headers are checked where the sources include them and the report names the header. `--enable=style` is not a choice: the addon's reports have severity `style` and without it cppcheck prints nothing (measured 2026-11-25: no line at all for a file with a `goto`). `--cppcheck-build-dir` is for the addon's rules that read every file together (the Rule 5 group, 8.4 to 8.6); the gate empties it first, a stale cache changes the answer. The compiler defines (`-D__GNUC__=<major> -D__GNUC_MINOR__=<minor>`, GCC's own or Clang's 4.2) are what `configforge_setup_cppcheck` already computes with the reason written (`cmake/ConfigForgeAnalysis.cmake:196-209`): the card moves that into `cf_cppcheck_compiler_defines(<out>)` used by both, not a copy. `-j` is the logical cores, at most 8: 32 s at `-j3` on the WSL machine (measured), about a minute expected on a 4-core runner.
  * **No rule texts, and how the gate works without them.** MISRA's texts are copyright (`docs/Compliance.md:121-122`). Without a `--rule-texts` file the addon's id is `misra-c2012-<N.M>` and its message the same sentence for every rule, category `Undefined`. The gate needs the number only: it matches `: misra-c2012-([0-9]+\.[0-9]+)$` on the template's output and makes the file relative to the source root. No rule text and no rule's category is committed. Directives are not reported by the addon at all (no `dir-` id among the 6,562 first-run reports) and stay on the review checklist (`docs/Compliance.md:135`). A `misra-config` line ("because of missing configuration, misra checking is incomplete"; 30 on the first run) is counted and printed in the summary and is never a violation: the report must say that "no violation" does not cover those places. The same file, line, column and rule from two sources (a header seen by many) is one report.
  * **The addon must have run: a canary.** Before the real run the gate checks a three-line C file with a `goto` and requires `misra-c2012-15.1` in the output. If it is not there the gate FAILS ("the MISRA addon reported nothing for a file that violates 15.1: python3 or the addon is missing, or cppcheck changed its output"), never a green with zero reports. A gate that fails open is worse than none.
  * **The record: `docs/compliance/deviations.txt`.** `docs/Compliance.md:98` says `deviations.md` and "planned"; a table in Markdown needs a Markdown reader in CMake and the record is read by a script, so it is plain text, and Compliance.md follows in step 11. One line a record, fields separated by ` | `; blank lines and lines starting with `#` are ignored; carriage returns are stripped (`cmake/gates/GateLimits.cmake:18-19` does the same):
    `<rule> | <file> | <count> | <kind> | <reason>`: rule `N.M` as the addon writes it; file the path from the source root, a file and never a directory; count the exact number of distinct reports of that rule in that file; kind `deviation`, `tool` or `backlog`; reason at least 12 characters and not `TODO`.
    `ignore | <rule> | <reason>`: a rule the gate does not read.
    `tool | cppcheck | <major.minor>`: the version the counts were made under; exactly one such line.
    A reason may not hold `;`, `[` or `]` (CMake lists would split or mangle it; the gate names the line). **File and count, not file and line** (the brief offered both; this card rejects the line): a line number moves with every edit and every format pass, so each card that touches a file would rewrite the record, and `docs/Codemap.md` and `docs/API.md` already show what citing lines costs. With a count, a new report in a file that already has the rule fails (the count is higher), a fix fails until the line is lowered or removed (the record no longer matches), and a report moved between files fails twice.
  * **The three kinds.** `deviation`: a decided, permanent departure, the reason naming its row in `docs/Compliance.md` "Where the standards disagree" or a D-number; allowed only for a file under `lib/*/src/`, never for a file in an `include/` directory (`docs/Compliance.md:82-88`: a deviation in a public header is one every user adopts). `tool`: the code complies and the addon is wrong, the reason saying why. `backlog`: a real report no one has decided on, counted and printed by kind; it cannot grow (the count is exact), and the first card to take a rule turns its lines into a fix (the lines go) or a `deviation` (kind and reason change). The gate does not enforce MISRA's classes (mandatory, required, advisory): the licensed rule list is not in the repository and a wrong number in a gate is a false claim; a reviewer checks them (organiser's answer 1).
  * **Ignored rules.** `ignore | 2.3`, `2.4`, `2.5` and `8.7`, each with the reason "a rule about a whole program: unused macros, types and tags, and an external name used in one file, are judged where the program is whole, by the integrator" (`docs/Compliance.md:90-94`). They are 225 of the 6,562 first-run reports. A report of an ignored rule is dropped before the count; an `ignore` line needs no report. No other rule is ignored.
  * **The first run: nothing is fixed, everything is recorded** (the count threshold asked for is **0**). Measured 2026-11-25 at `d3bb03a` with cppcheck 2.19.0-3 (Ubuntu 26.04, the package CI installs) on the `misra` build: 6,562 reports, 225 in the four ignored rules, so **6,337 to record, in 613 (rule, file) lines, 55 rules, 131 of the reports in `include/` directories**; the largest are 15.5 (about 1,700), 12.1 (about 1,600), 10.4 (about 1,000), 17.7, 5.9 and 18.4 (about 330 each). Why 0: of the low-count rules the ones read are deliberate or the addon's error, not slips (`lib/base/src/alloc.c:23` and `:28` are the allocator's own `malloc` and `free`, rule 21.3; `lib/platform/src/posix/posix.c:47` is the octal `01000` of `S_ISVTX`, 7.1; `lib/serialize/src/json.c:954` is a codec descriptor, 8.4; `lib/config/src/core/define.c:670` a `qsort`, 21.9; `posix.c:173` is `(void)fn;` reported as 11.1), so a fix is a judgement per site, and a commit that changes code six thousand times to quiet a checker is how a gate loses the trust it was made for. The ratchet makes the later cards cheap: each lowers a line.
  * **First kinds and reasons**, applied once with a throwaway script (under `/mnt/d/cf-work`, not committed), after which `-DWRITE` keeps them:
    * `15.5` `deviation`: "docs/Compliance.md, 'One exit per function': early return on error is the house style (docs/Conventions.md)".
    * `21.3` `deviation`: "docs/Compliance.md, 'Dynamic memory': every allocation goes through the allocator interface (D-03) into an arena, and cf_arena_fixed needs no heap".
    * `21.6` `deviation`: "docs/Compliance.md, 'Standard I/O': confined to the file sources and the platform layer; a build from memory calls none of it".
    * `17.2` `deviation`: "docs/Compliance.md, 'Recursion': the depth is bounded by the depth limit and D-82's budget".
    * `17.3` (19 reports, all in `lib/platform/src/posix/posix.c`: `opendir`, `readdir`, `stat` "implicitly declared" because cppcheck reads no system header): first try `--library=posix` in the command (step 7); if the reports go, the flag stays and there is nothing to record; if not, `tool`: "cppcheck reads no system header, so a POSIX function is undeclared to it; the file includes <dirent.h> and <sys/stat.h> and the build's -Werror refuses an implicit declaration".
    * Any report whose file is under an `include/` directory, of any rule above: `backlog`: "a public header takes no deviation (docs/Compliance.md, 'The public headers come first'); a later card fixes it".
    * Every other rule: `backlog`: "not yet examined: the first run of gate.misra (N-19); the card that takes this rule turns the lines into a fix or a deviation".
  * **Where it runs.** A ctest gate `gate.misra` registered in `cmake/ConfigForgeGates.cmake` only when `CF_BUILD_PROFILE_NAME` is `misra` (`cmake/ConfigForgeProfile.cmake:276`) and after the MSVC `return()` (`ConfigForgeGates.cmake:165-166`: the gate drives cppcheck with GCC's defines), with `TIMEOUT 900`. The list of defines goes through `-D` joined with `|` and split back as `features` does (`ConfigForgeGates.cmake:23`, note at 52-54). Without `cppcheck` the gate prints `gate.misra: skipped, cppcheck is not installed` and exits 0, as the optional gates do (`cmake/gates/GateAmalgamation.cmake:27`); **but when the environment variable `CI` is `true`** (GitHub sets it) it fails instead, so CI cannot go green by lacking the tool. The same for a cppcheck whose major.minor is not the record's `tool` line: a status line naming both versions locally, a failure in CI (the counts belong to a version; an apt update that moves it is a chore that `-DWRITE` does, not a green by accident). CI: the `profiles` job already builds and tests `misra` (`.github/workflows/ci.yml:171-180`) and does not install cppcheck; the `analyze` job (506-512, the one with cppcheck) builds the default profile, whose compile database is not the profile's. So `cppcheck` joins the `apt-get install` line of `profiles` (line 178; the other profiles ignore it: seconds). It is **not** added to `scripts/verify.cmake`'s presets (a configure and build of another profile and a minute, on every verify): the carrier runs `cmake --preset misra && cmake --build --preset misra && ctest --preset misra -R gate.misra` in WSL by hand, as the loop's "every `gate.*` test" asks.
  * **Suppressions.** None: `--inline-suppr` is not passed, and the gate also fails if a file under `lib/` holds `cppcheck-suppress` followed by `misra` (none today): a comment that hides a report is a record the gate cannot count, and the record file is the only place.
  * **`-DWRITE=<file>`**, a mode of the same script (as `scripts/generate/limits.cmake`'s is): writes the record for the reports found. For each (rule, file) the kind and reason of the line that exists there, else of any line of the same rule, else `TODO`; the count made current; lines whose reports are gone dropped; `ignore` lines kept; the `tool` line takes the running version; sorted by rule number, then path. It makes a fix cheap (fix, `-DWRITE`, read the diff) and the first fill possible. The gate never writes unasked.
  * **The comparator is tested without cppcheck.** `GateMisra.cmake` takes `-DOUTPUT=<file>` (cppcheck's output already made) and then runs no cppcheck: the same code compares it with `-DRECORD=<file>`. The test `misra.compare`, in every profile and on every platform (CMake only), drives it with hand-written outputs and records. The cppcheck run itself is the real `gate.misra`.
  * **The summary line** on success: `gate.misra: <N> reports in <F> files and <R> rules, <K> record lines (deviation <d>, tool <t>, backlog <b>); <h> reports in public headers; <m> misra-config notes; ignored rules: <list>; cppcheck <version>`. The compliance report as a release artifact (`docs/Compliance.md:133`) is a later card; this line is its first data.
